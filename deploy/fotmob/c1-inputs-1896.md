# Входы C1 (#1896)

Код подготовлен для отдельной задачи изолированного контура. Это не разрешение
установки, bootstrap или запуска SQL на общем Trino. Они требуют согласованного
окна по брифу #1896. Ничего из перечисленного в sandbox не выполнялось.

## Контракт и обновление

`scrapers/fotmob/c1_inputs.py` создаёт Bronze `fotmob_c1_inputs`, partition
`deadline_day`, natural key `(deadline_day, competition_id, source_season_key,
match_id)`. `kind=input` хранит восемь прежних входов классификатора;
`kind=day` — обязательный маркер полного дня, включая пустой. Служебный checkpoint
лежит в партиции `1970-01-01`, `kind=checkpoint`. Это одна постоянная таблица;
временные `fotmob_c1_candidates__stg_*`/`fotmob_c1_inputs__stg_*` удаляются после работы.
При аварийном завершении их остатки убирает штатный janitor, без обхода пломб.

Checkpoint содержит IDs Iceberg snapshots и отпечатки файлов по физическим
партициям. Новые/удалённые файлы, изменения scope/seasons и manifest (EXCEPT ALL
между snapshot IDs, включая удаление и кратность) определяют затронутые сезоны.
Обработанные IDs продвигаются только вместе с данными одним атомарным MERGE.
Истёкший snapshot — отказ с алертом, требуется согласованный rebootstrap.

Чтение закреплено за snapshots под существующим writer lease FotMob. Перед MERGE
проверяется неизменность source IDs; lease проверяет штатный инструментированный
manager. Непустота пачки, v2/v1 и tombstone выбираются до фильтра дат, по полным
партициям сезона. Кандидаты записываются в CTAS один раз: дальнейший SQL не
разворачивает current повторно. Связанные natural keys одного match_id включаются
до неподвижной точки, чтобы сохранить прежние глобальные fi/h/snap, не схлопывая
строки результата. `fi` по-прежнему учитывает неподтверждённые payloads, `h` — всю
историю, `snap` — нижние границы D−4/D−3 без верхней границы.

Кэш содержит и будущие сроки текущего календаря, начиная с bootstrap first_day.
Поэтому новая дата открывает только marker; календарь заново не строится.
Перенос/удаление/изменение scope заменяет все ключи затронутого сезона, включая
будущие даты и старую дату переноса. Исчезнувшие строки удаляет тот же MERGE.

Reader делает один скан партиции дня. Пустой полный день даёт NULL-заглушку.
Нет marker, marker неполный/дублирован или публикация старше двух часов UTC — SQL
ошибка измерения, а не due=0. Это защищает pending-переоценку после отказа updater.
При неизменных исходниках старые input-строки сохраняют собственный generation,
а свежий day-marker удостоверяет проверенный checkpoint всего набора.

## Доставка и первичное заполнение — владельцу после разрешения

DAG `dag_refresh_fotmob_c1` виден только при `FOTMOB_ISOLATED_STACK=1`, изначально
на паузе, каждый час в :15, max_active_runs=1, без повторов, timeout 30 минут;
`DEFAULT_ARGS.on_failure_callback` отправляет штатный алерт. Каждый запрос updater
ограничен серверными query_max_run_time/query_max_execution_time=300s.
Bootstrap через dag_run.conf запрещён. Parser version, batch identity и сборщик
не изменены. Изменений Compose/cron/доставки нет. DAG придёт только штатной ночной
доставкой (одна за ночь); до конца действующей приёмки источника не выкатывать.

В отдельном утверждённом окне вызвать `refresh(manager, first_day='2026-10-20',
last_day='2026-10-27')` под `maintenance.writer_lock()`, привязав полученный lease
через `manager.set_write_authority(authority)`. Manager —
`FotMobTrinoTableManager(source='fotmob:c1-inputs', session_properties={
'query_max_run_time': '300s', 'query_max_execution_time': '300s'})`.
Первичное чтение истории может быть тяжёлым; время updater здесь не измерено.
После успешного bootstrap и проверки открыть расписание DAG.

`morning-report-c1-inputs.patch` накладывается на живой `morning_report.py`, меняет
только `_c1_sql`. Классификатор, округление, pending и заморозка state остаются
байт-в-байт. Патч #1299 не нужен. Применять после bootstrap/сверки; общий хостовый
файл в этой задаче не менялся. Старый C1_SQL_TIMEOUT_S остаётся прежним согласно
границе брифа; пяти минут для приёмочного запроса добиваются отдельной сессией.

## Одна приёмочная сверка — лидом

`read_sql('2026-10-20', '2026-10-23', include_day=True)` строит один SELECT с явным
диапазоном четырёх партиций и календарём дней. Выполнить его один раз с серверными
query_max_run_time/query_max_execution_time=300s и внешним общим deadline. При
превышении отменить query ID и подтвердить terminal state до нового действия;
повторов и старого тяжёлого SQL не запускать. Сохранить query ID, wall time,
scanned bytes/splits и JSON строк, время оценки now (UTC без tzinfo), копию state.
SQL builder сам запрос не выполняет. Лимит времени и подтверждение отмены —
обязанность согласованного live-раннера лида; DuckDB этого не доказывает.

Локально разделить строки по первому полю deadline_day, удалить его и вызвать
неизменённый `_c1_classify(rows, now=fixed_now)` из сводки. Для каждого дня сравнить
`due`, `ok` и `pct` с `state['days'][d]`; pct — Decimal HALF_UP до 0.1, как в
`_c1_measure`. State не писать. NULL-заглушки игнорирует сам классификатор.
Совпадение этих трёх значений не доказывает исторические gap/late/pending.
Отличия требуют объяснения и решения владельца. После успешной сверки тем же
лёгким reader считаются 24–27.10; восполнение state и серии — отдельный разрешённый
приёмочный шаг по #1896, штатная сводка сама пропущенные дни не дописывает.

Готовность production и ≤300 секунд пока не подтверждены: нужны этот единственный
live-замер, сверка четырёх дней, bootstrap и приёмка, которые запрещены исполнителю.
