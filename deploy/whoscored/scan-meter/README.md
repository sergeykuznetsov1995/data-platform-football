# Учёт физических сканов WhoScored в Trino 484

Обработчик Java записывает одно событие на каждый полученный от Trino Iceberg `ScanReport` для таблиц `bronze.whoscored_*` и `ops.whoscored_*`. Запись содержит исходное время события, таблицу, снимок, наносекунды планирования, идентификатор экземпляра и порядковый номер. Обычный журнал Trino отдельно содержит начало каждого непустого `SnapshotScan`. SQL одного запуска может породить несколько физических сканов.

## Подготовка выпуска

Используйте проверенную ревизию, точный образ координатора и фактические Compose-файлы из метаданных контейнера. Сохраните хеши исходных настроек, версию Java, идентификатор контейнера и результаты базовых проверок из регламента общего Trino. Сборка на стенде требует JDK 17 или новее.

```sh
javac --release 17 -Xlint:all -Werror -d "$classes" deploy/whoscored/scan-meter/ScanJournal.java
jar --create --date 2026-11-20T00:00:00Z --file "$release/football-whoscored-scan.jar" -C "$classes" .
```

Соберите JAR в пустом каталоге классов. В `$release/logging.properties` скопируйте действующую конфигурацию java.util.logging координатора и добавьте содержимое `logging.fragment.properties`. При стандартной настройке база находится в `$JAVA_HOME/conf/logging.properties` образа. Проверьте существующие явные параметры JUL перед объединением. Скопируйте действующий `jvm.config` в `$release/jvm.config` и задайте в копии один параметр `-Djava.util.logging.config.file=/etc/trino/whoscored-scan.logging.properties`. Сохраните остальные параметры запуска и настройки Airlift, включая основной журнал запросов.

Подготовьте постоянные каталоги `$state/control` и `$state/journal`. Координатор читает первый и пишет во второй. Только оператор изменяет срок в `control/until`. При запуске контрольный каталог пуст. Ограничьте доступ к файлам и проверьте свободное место. Размер одного журнала 8 МиБ, число файлов в кольце 16. Сохраняйте закрытые отрезки до перезаписи. Даже при низком трафике проверяйте непрерывность порядковых номеров.

Задайте абсолютные пути `WHOSCORED_SCAN_METER_RELEASE` и `WHOSCORED_SCAN_METER_STATE`. Добавьте `scan-meter.compose.yaml` последним к действующей конфигурации. Сравните штатный и новый вывод Compose в памяти, сохранив только различия в монтировании для Trino и хеши. Все пять новых путей назначения приведены в overlay. Проверьте совпадение образа, параметров памяти, сетей и прочих служб.

## Включение и откат

Установите обработчик в согласованное окно общего Trino, после завершения активных запросов и проверки возможности отката. Используйте фактические файлы проекта и команду `up -d --no-deps trino`. Проверьте образ, health, число перезапусков, RSS, доступность каталога, очередь запросов и исходное время ответа контрольного чтения. Сверьте их повторно под обычным трафиком. Регламент платформы задаёт для RSS предел 80% cgroup и для контрольного чтения 10 секунд. [Регламент общего Trino](../../../docs/operations/trino-shared-server-1937.md)

Запишите в `control/until` время окончания согласованного наблюдения в UTC в формате ISO с `Z`. Заменяйте файл атомарно внутри смонтированного каталога. Обработчик проверяет срок каждые 15 секунд. Пока он активен, Trino форматирует отчёты Iceberg всех источников до отбора таблиц WhoScored. Сравните нагрузку координатора до и после включения на сопоставимом трафике. После первого обращения к Iceberg дождитесь строки `WS_SCAN_HEALTH1` с активным обработчиком и пустой очередью. Сделайте контрольное штатное чтение и сверьте число начатых и завершённых сканов. Для интервала требуется предыстория не меньше минуты.

При ухудшении работы или окончании срока запишите прошедшее время либо удалите файл `until`. Убедитесь, что очередная контрольная строка показывает `false`, счётчик стабилен, штатный Iceberg-запрос работает и нагрузка вернулась к исходной. Для полного возврата прежней конфигурации при штатной остановке используйте полный исходный набор Compose-файлов без этого overlay и ту же команду для одного Trino. Проверьте исходные настройки и новую строку запуска. Период отключения отмечайте как пробел учёта.

## Проверка интервала

Снимайте обе части доказательств с одного неизменного идентификатора контейнера. Укажите полный перечень таблиц источника, включая таблицы с нулём событий. Передайте стандартный вывод `docker logs` и его поток ошибок в `select-console` через shell с `pipefail`. Сохраняйте только выбранные и очищенные записи. Для повтора используйте диапазон времени и тот же ID контейнера. Для фильтров и текста SQL места в выходном файле нет.

```sh
set -o pipefail
docker logs --since "$before" --until "$after" "$container_id" 2>&1 |
  python3 scripts/ops/whoscored_scan_journal.py select-console > "$evidence/console.jsonl"
python3 scripts/ops/whoscored_scan_journal.py verify \
  --start "$start" --end "$end" --tables "$evidence/tables.json" \
  --console "$evidence/console.jsonl" "$evidence"/segments/*.tsv > "$evidence/scans.json"
```

Скопируйте соответствующие файлы кольца в каталог `segments`. Идентичные повторы одного порядкового номера допустимы, несовпадающие повторы требуют проверки. Выберите границы захвата с полностью записанными контрольными точками, покрытием предыдущих 60 секунд и закрытием начатых сканов. При пересечении границы долгим сканом расширьте захват. Пропущенное событие, смена экземпляра, пропуск контрольной точки, переполнение, ошибка записи или неполная строка дают ненулевой код и лишают интервал зачёта.

Поле `scans` считает события в полуоткрытом интервале суток. `peak_60s` даёт наибольшее число событий в любой скользящей минуте, включая начало суток. В итог для #2128 добавьте отдельные доказательства по пользователю Trino, штатным запускам обеих полос, коммитам и опросам манифестов. На синтетическом стенде сверяйте каждое завершение по таблице, снимку и длительности с независимым REST-приёмником.
