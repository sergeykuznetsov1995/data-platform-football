# Контроллер истории SofaScore (#1363)

Контроллер истории работает по фактическому долгу завершённых матчей. Порядок:
текущие сезоны ядра → последний завершённый сезон каждого турнира → июльский хвост
→ десять предыдущих сезонов каждого турнира → глубже → спорные корзины.
«Десять» означает записи исходных сезонов по турниру, а не календарные годы.
Студенческие турниры и киберфутбол исключены через `denominator.tsv`.

## Покрытие и переходы

Один матч закрыт только при `capture_complete=true` в Bronze и пяти терминальных
записях canonical manifest с `freshness_key=final` и точными исходными ID турнира,
сезона и матча. Статусы `success`, `legitimate_empty`, `not_supported` терминальны;
`schema_error` и `retryable_failure` не закрывают матч. Старый `state.json` не
подтверждает процент закрытия. Отказанные строки и карантин остаются долгом.

При каждом новом DagRun контроллер читает две групповые выборки Bronze/manifest.
Будущие или идущие матчи в афише определяют текущий сезон. Успешный `season`
в сохранённом отчёте подтверждает обход цепочек страниц; успешный `matches`
этого не доказывает. Без полного обхода покрытие неизвестно. Турниры ядра,
которых нет в snapshot или у которых нет применимых сезонов, показываются как
неизвестные, а не исчезают из гейта. Проверенная пустая афиша — известный ноль.
Пополнение snapshot по-прежнему регулируется политикой кампании и отдельными
задачами; контроллер её идентичность не меняет.

Группа3 доступна только при **каждой** из групп1/2 ≥99% по матчам ядра, без
неизвестных скоупов. При новом долге ранняя группа снова получает приоритет.
Сравнение целочисленное; округление строки сводки не открывает гейт.
Группа1/2 может быть пустой только при известном полном покрытии.

Внутри группы выдаётся не более одного сезона турнира в порции. Устойчивый
курсор проходит сезоны вширь, затем следующую глубину. Парковка сохраняет
cooldown, карантин сохраняет привязку к релизу/контракту сопоставления сезона.
Карантин глубокого сезона не мешает перейти глубже, но в сводке не считается
закрытием. Опубликованный скоуп с отказанными строками переигрывается один раз
на новом релизе, а не в каждом непрерывном прогоне.

## Состояние и рестарт

Новый `history-controller.json` лежит рядом с `state.json`. Существующие
`state.json` и `failures.json` сохраняют схему1. Файл содержит позиции групп,
наблюдаемое покрытие, июльскую когорту и последний неизменяемый план DagRun.
Блокировка, временный файл, `fsync`, атомарная замена и `fsync` каталога
защищают резервирование. Digest плана выявляет повреждение JSON.

Повтор того же DagRun получает прежние ID и `run_id`. Новый DagRun не может
переписать незавершённую резервацию. Если Airflow подтверждает прежний DagRun
терминальным, планировщик завершает его учёт штатным finalizer перед новой
выдачей. Старые ID сохраняются как retired digest: поздний повтор не выдаёт
новую аллокацию. Чужая кампания, повреждённый checkpoint и неопределённое состояние
старого DagRun отклоняются. Пауза DAG и параметры шлюзов этим кодом не меняются.

## Формы и июльский хвост

Статическая политика покрывает положительное число команд, включая1–7,
49–64 и65+. Шесть добавленных классов имеют фиксированный потолок473059байт,
не выше прежнего максимального сезонного класса. Прежние классы, ID и бюджеты
сохранены. Превышение потолка — обычная ограниченная ошибка попытки; отсутствующая
в политике форма — ошибка конфигурации, не вечный `deferred`.

Неизвестное число команд имеет явный `team_count_pending`: placeholder для
загрузки medallion-конфигурации не разрешает сезонный захват. Формат без
канонического сопоставления показывает `mapping_required`, не закрытие.

Июльская когорта — строки `match_stats`, впервые загруженные в июле2026,
без `events` при первом наблюдении. После частичной публикации матч остаётся
в когорте до полного закрытия. Сохранённые ID перечитываются независимо от
текущей даты `_ingested_at` статистики; отсутствие ответа остаётся неизвестным. Дата матча может быть гораздо старше июля2026.
Пара турнира/сезона разрешается однозначно; неоднозначные и отсутствующие в
snapshot пары показываются отдельно. Порция — максимум25матчей с полным raw
в первую очередь. Полный список HMAC-подписан штатным workload plan; runner
сверяет его и использует точные ID даже без строки schedule. Смена списка
в той же попытке запрещена. `force_replace` и переименование `final` не нужны.
Успех июльской порции не помечает весь сезон завершённым в старом state.

## Свoдка и offline-проверка

`plan_historical_batch` публикует `history_groups` и `history_summary` в XCom;
те же данные находятся в checkpoint. Строка показывает закрыто/всего, процент,
долг, неизвестные скоупы, pending/mapping, parked и quarantine по каждой группе.

Полностью offline-команда, с сохранёнными входами:

```bash
python scripts/research/replay_sofascore_history.py \
  --snapshot <saved-snapshot.json> --state <saved-state.json> \
  --inventory <saved-inventory.json> --checkpoint <scratch-checkpoint.json> \
  --run-id offline-rehearsal --output <evidence.json>
```

Inventory содержит `observed_at`, `scopes` с исходными ID, `finished`, `closed`,
`ongoing`, `schedule_complete` и при необходимости `july_match_ids`,
`july_raw_match_ids`, `july_closed`, `july_unresolved`, `july_cohort`. Старые
агрегаты без доказательства публикации не превращаются в подтверждённые проценты.
Команда не соединяется с источником или Bronze и не публикует данные.

Подключение строки к хостовой утренней сводке — отдельная установка:
прочитать checkpoint из runtime, передать `groups` в `render_summary` модуля
из установленного релиза; отсутствие/ошибку чтения показать как неизвестное.
Не запускать сбор из сводки. В этом PR хостовая сводка, cron и watchers не меняются.
Merge, доставка, установка, возобновление истории и production-приёмка отдельны.
