# FotMob #1289: восстановление записи Bronze и очистка staging

`scripts/fotmob_cleanup.py --isolated-stack` предназначен только для старых
временных таблиц Bronze из [изолированного контура без церемонии](fotmob-isolated-ceremony-free.md).
Это отдельный режим. Без флага действует прежняя процедура с pause evidence,
deployment report и остановкой scheduler. Перенос этой процедуры на изолированный
контур не требуется.

Реализация проверяется на подставных клиентах и процессах. Наличие этого документа
не разрешает удаление production-таблиц, доставку кода или изменение действующих
пауз. Применение требует отдельного согласованного плана очистки и штатно
доставленной версии скрипта.


## Пачки и прерывание записи

Batch ID и parser version `fotmob-native-v2` сохраняются. Сверка читает только
пачки, которые есть в текущем буфере. Она сравнивает SHA-256 отпечатки значений
строк и количество одинаковых строк. Порядок строк и служебные отметки
наблюдения не влияют на результат. Значения приводятся к типам колонок Trino.
Точный повтор одного dataset не добавляет второй физический набор; отдельные
наблюдения скоупов и новых запусков сохраняются в манифесте.

Для field inventory сравниваются только логические ключи, которые эта попытка
ещё должна записать. При смене порядка целей ранее записанная пачка может
содержать больше ключей. Такой размер сам по себе не является ошибкой.
Несовпадение обычной пачки, подтверждённой успешным манифестом, приводит к отказу
без удаления данных. Пачка без успешного подтверждения восстанавливается из
нового полного dataset. Диагностическая строка `interrupted` не запрещает это
восстановление и не публикует данные через current views.

TERM останавливает сбор и отменяет активный SQL. Отдельное исключение проходит
через обычные обработчики ошибок Trino и финального flush. Runner записывает
`interrupted` для незавершённых наблюдений, если может получить свободный замок.
Ожидание занятого замка при этом отключено. При потере права записи диагностический
манифест также запрещён; следующая попытка сверяет фактические строки. Успех,
который успел попасть в манифест до потери ответа, не заменяется прерыванием.
После TERM runner не обновляет current views и не запускает salvage payload flush.
Повторный TERM не прерывает диагностический выход; SIGKILL остаётся окончательным.

Замок удерживается на время физической записи. Владение проверяется в той же
сессии PostgreSQL перед SQL и во время его исполнения. Потеря сессии или права
необратимо запрещает следующие записи в этом процессе и отменяет текущий запрос.
Исход уже отправленного SQL может быть неопределённым; его проверяет следующая
попытка по строкам и манифесту. Новое соединение не восстанавливает утраченное право.
Потерянный ответ изменяющего SQL не вызывает слепого повторения INSERT.

Обработанное прерывание убирает собственный staging, пока целевая таблица ещё не
начала меняться. Если целевой SQL уже отправлен, staging сохраняется для
восстановления. SIGKILL не может выполнить обработчик очистки: оставшиеся таблицы
удаляет отдельная согласованная операция ниже.

## Что проверяет режим

Вызов с хоста задаёт точный 64-значный `--scheduler-container-id`, абсолютный
`--release-root` и полный 40-значный `--release-sha`. Допустим только проект
`fotmob-airflow` и его работающий сервис `airflow-scheduler`. Скрипт читает
Docker inspect и проверяет маркеры `FOTMOB_ISOLATED_STACK=1`,
`ALERT_ENV=fotmob-isolated`, отсутствие настроенной церемонии и собственную
Airflow metabase. Пять каталогов кода должны быть readonly bind mounts из заданного
дерева. Подмены кода вложенными mounts запрещены; readonly `.airflowignore`
разрешён по рецепту контура.

Git HEAD должен совпасть с SHA. Дерево должно быть чистым. Скрипт проверяет байты
всех отслеживаемых файлов в смонтированных каталогах по Git blob и затем внутри
контейнера по SHA-256. Неотслеживаемый код, включая игнорируемые файлы, запрещён;
сгенерированный bytecode допускается. Процесс cleanup не записывает новый bytecode.

План и выполнение запускаются через `docker exec` в конкретном контейнере.
Клиент Trino и общий замок писателя используют его фактическое окружение.
Приоритет `FBREF_CONTROL_DB_URI` сохраняется как у раннера. Произвольная метабаза
из окружения хостового процесса не используется. `--trino-env-file`,
`--pause-evidence` и `--deployment-report` в этом режиме отвергаются.

План фиксирует Trino nodes, контейнер, SHA и отпечаток привязки окружения.
Выполнение сравнивает их с текущим состоянием. Пароли, URI метабазы и полное
окружение в отчёт не включаются. Общий control DB gate публикации не вызывается
для доказанного изолированного контура без церемонии.

## Граница удаления

`plan --isolated-stack` читает staging и фиксирует точные имена, row count,
snapshot ID, время snapshot и порог возраста `--older-than-hours` (по умолчанию
24 часа). Допускаются только имена по регулярному выражению
`^fotmob_[a-z0-9_]+__stg_[a-z0-9_]{1,128}$`. План действует до 24 часов.
Inventory и таблицы динамического каталога сохраняются. Чтение inventory,
компакция и обмен таблиц в этом режиме отсутствуют.

`execute --isolated-stack` требует файл `--plan`, его точный `--plan-sha256`
и `--confirm EXECUTE_REVIEWED_FOTMOB_CLEANUP`. План должен быть создан этим
режимом для того же контейнера, runtime и Trino. Строки нового плана не объединяются
со старым автоматически. Изменение snapshot, row count или времени любого
существующего target останавливает выполнение до первого DROP. Уже отсутствующий
точный target допускается для повторения после прерванного исполнения.

Одна живая сессия advisory lock FotMob удерживается во время проверки runtime,
состояния Airflow/Trino, всей проверки таблиц, всех DROP и итоговой проверки.
Активные FotMob runs/tasks или SQL-записи приводят к отказу. Перед каждым DROP
проверяются runtime и lease. Монитор lease отменяет Trino cursor при потере
соединения или замка. Отключённый замок не допускается.

Режим не меняет DAG pauses, hold, STOP, campaign-журнал и настройки. Он не
останавливает, не перезапускает и не создаёт контейнеры. При отказе команда
завершается с ненулевым кодом и пишет JSON evidence в `--output`. После DROP нет
возврата удалённой staging-таблицы; незавершённый отчёт требует проверки фактических
таблиц по тому же reviewed plan перед повтором.

## Проверка реализации

Из отдельной development worktree, без production и сетевых вызовов:

```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 PYTHONDONTWRITEBYTECODE=1 \
  /root/.venvs/dpf-test/bin/python -m pytest -q -p no:cacheprovider \
  tests/unit/scripts/test_fotmob_cleanup.py
```

Тесты проверяют прежний церемониальный путь, отсутствие чтения inventory,
проверку всех targets до первого DROP, удержание одного lease и отмену cursor,
а также отказ при чужом контейнере, writable/чужом mount, изменённом runtime,
активной записи, отключённом замке и несогласованном SHA плана.
Отдельная регрессия убивает собственный процесс через SIGKILL после сохранения
staging в файловом подставном каталоге. Новый процесс выполняет проверенный план
под одним lease с монитором cursor и удаляет только этот target. Остальные staging
и inventory сохраняют содержимое. Реальные PostgreSQL, Trino и Docker не вызываются.
