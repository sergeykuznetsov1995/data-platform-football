# FotMob: ночной отказ #1288 и подготовка доставки #1289

Ночная волна `fotmob_orchestrated__e9fffb7f-976b-54b4-a77b-bf88286cb40c`
09.10.2026 закрыла17/17 запланированных скоупов и записала16999 строк.
451 операция трансферов отказала из-за неизвестных корневых полей
`minAge`, `minDate`, `maxMarketValue`. Шесть операций discovery отказали
из-за отсутствующих календарей. Отсутствие исключения `__main__` не доказывает
`no_progress_failure`: отчёт показывает продвижение и ошибки операций.
Автомат откатил runtime на `cd7b6e68` в01:01:34UTC (04:01:34МСК).

## Контракт исправления

Три поля трансферов — границы фильтров страницы. Они сохраняются raw-only;
правила точные, неизвестные соседние и вложенные поля по-прежнему дают drift.
События, пагинация, parser version и batch identity сохраняются.

Сохранённые страницы10056,9170,10433,10840,9669,300 содержат корректные
сезоны, но календарные виджеты имеют только `hasOngoingMatch:false`,
`tabs=[]`, `stats={}`, `table=null`, `playoff=null`. Тела существовали
до ночного отказа. Discovery принимает только метаданные сезонов и полный
учёт JSON-путей; выбранного `SeasonBundle` при этом нет.

Parser продолжает отвергать отсутствующий календарь через
`CalendarMissingError`, подкласс `CatalogShapeError`. Только точный проверенный
виджет без альтернативных календарных полей может считаться временно
недоступным. При отсутствии ранее принятых матчей обычный сбор записывает
`retryable_failure/source_calendar_unavailable`, не публикует строки матчей
и не закрывает скоуп. Сбой проверки истории запрещает публикацию. Если матчи
уже были, отказ остаётся schema drift и сохраняет прежние данные.
REPLAY сохраняет строгий отказ. Повреждённый явный календарь, неизвестный путь
или другой виджет не получают это послабление.

При продвижении другого скоупа штатный runner может вернуть `partial_success`;
без продвижения остаётся `rc=1`. Успешные трансферы сами по себе не считаются
продвижением скоупа. Недоступные календари остаются в included-знаменателе
и незавершённом долге; это не доказательство их сбора.

catalog.py, parsers.py, service.py и по перечитыванию шести активных своих DAG
строго после доставки. import errors=0; паузы, контейнеры, mounts, hold/STOP,

`partial_success` не означает полноту данных.

`current-acceptance.sql` и `finished-without-payload.sql` из task1288/delivery:

## Существующая история — отдельный пакет и разрешение

Подготовленная копия `operational/prepared/driver.sh` сохраняет entities,
queue и подпись плана. Она начинает юнит только после19:05UTC (22:05МСК)
при отсутствии running/queued актуалки. Последний старт — до23:10UTC
(02:10МСК). Узкий writer lock больше не отменяет эти условия. Больший
UNIT_TIMEOUT автоматически сокращает окно; нулевой timeout запрещён.
Общий60rpm сохраняется.

После docker exec драйвер проверяет отсутствие процесса своего точного run_id.
Код выхода host-timeout не заменяет эту проверку. Живой процесс или недоступная
проба останавливают драйвер с FAILED, без продвижения курсора и новых юнитов.
Проверить собственный процесс до следующей актуалки; процессы#1185 не трогать.

Установку копии и обновление прежнего status.md, снятие hold/STOP и запуск
через существующий автомат разрешает владелец отдельно, после приёмки актуалки.
Не создавать новую кампанию и не обнулять done, parked, attempts или iter.

пересчитать по свежим журналам. Первый юнит принимается только по фактическому
completed_scopes и отсутствию оставшегося процесса; затем проверить актуальную
волну и задержки. Полная приёмка актуалки — три суток подряд с≥99% по утверждённому
критерию24часов, а не цвет первой волны.
