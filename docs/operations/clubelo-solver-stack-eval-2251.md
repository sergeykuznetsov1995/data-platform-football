## 1. Свидетельства и реализованная метрика

Команда воспроизведения (офлайн, только чтение фикстуры):


Реализация — офлайн-расчёт по режиму `daily_aggregates`, а не производственная телеметрия.
«Присоединённый» вход на уровне попыток — будущий контракт (раздел 2), а не уже
реализованная наблюдаемость.

Метрика условная: S/D = solved/detected, то есть доля корректно решённых среди обнаруженных
challenge-событий, а не доля успешных попыток среди всех попыток. Детекция не покрывает
пути до выдачи challenge и часть таймаут-путей; выборки крошечные и селективно отобранные.
Наблюдаемое изменение — это не вероятность для произвольной попытки и не доказательство
корневой причины.

## 2. Классификация и будущий присоединённый контракт

Понятия на уровне одной попытки:

- A — начатые попытки;
- T — терминальные исходы через туннель/прокси;
- D — обнаруженные challenge;
- S — корректно распознанные решённые;
- V — строгая валидация транспорта;
- P — первый результат данных после валидации.

Соотношения (верны только для одной полной присоединённой популяции попыток):
S ≤ D ≤ A; T ≤ A; V ≤ A; T + V ≤ A. T и D могут пересекаться; равенство A = T + D
неверно. V НЕ обязано быть подмножеством S: ответ без challenge тоже может проходить
валидацию, а S не гарантирует V. 403 после валидации — отдельный исход (P), а не часть
S/V.

В дневных сохранённых данных A/T/V и их пересечения — UNKNOWN/null, никогда не ноль.
Успешные руны могут содержать неудачные попытки; ретраи создают экспозицию, зависящую от
исхода (outcome-dependent exposure).

Будущая запись попытки (контракт, а не реализация): source; идентификаторы attempt/run;
task try; порядковый номер bootstrap; идентификаторы lease и сессии солвера;
actual_start_utc / end_utc (логическая дата учитывается отдельно); tri-state
detected/solved/validated; терминальный исход; первый результат данных; задержки;
digest образа и версия браузера; join_complete. Группировка строго по actual_start_utc
(UTC). Дубликаты, неоднозначные join и отсутствие обязательного поля — fail closed;
никогда не смешивать такие записи с агрегатами. Это только контракт; наблюдаемость #2246
остаётся отдельной работой.

## 3. Будущий изолированный канареечный тест (только план)

### 3.1. Кандидат и неизменность текущего стека

Кандидат: отдельный сервис/проект, образ FlareSolverr с закреплённым digest и
фиксированной версией Chrome, изолированные состояние/сессии и лимиты ресурсов.
Выделенный будущий раннер маршрутизирует ТОЛЬКО ClubElo-канарейку на кандидата.
Существующий общий контейнер, конфигурация и производственный DAG не затрагиваются.
Правила gateway/pool/lease одинаковы в обоих плечах; история исключена; перенос
clearance запрещён; максимум один активный bootstrap кандидата. Сохранить ровно
3 попытки, паузу 10 с, таймауты 90 с (challenge) / 120 с (клиент), строгую валидацию,
ClubEloBlocked и все гарантии. Изменений ретраев/гард нет.

### 3.2. Дизайн и пределы

Контроль — текущий стек. Рандомизируются ЦЕЛЫЕ руны 1:1 в предзаявленных UTC-блоках
тайм-слотов; все ретраи остаются внутри своего плеча. Минимумы НА ПЛЕЧО: 30 detected,
40 попыток, 20 рунов. Жёсткие потолки: 30 календарных дней; 60 рунов на плечо
(120 всего); 240 начатых bootstrap-попыток всего; 2 старта bootstrap в минуту;
10000 браузерных/asset HTTP-запросов всего; 2 GiB трафика провайдера всего. Более строгие
существующие лимиты lease/gateway имеют приоритет. Если хотя бы один итог нельзя измерить
и контролировать до запуска — план НЕ ГОТОВ. Недонабранное окно — inconclusive;
автоматического продления и дополнительного трафика нет.

### 3.3. Числовые критерии успеха (после достижения минимумов)

- S/D кандидата ≥ 90% и разница кандидат − контроль ≥ 20 п.п.; нижняя односторонняя
  95%-я граница для разницы > 0 (кластерный по рунам бутстреп, детерминированный,
  предзаявленный: 10000 реплик, seed 2251). Если контроль восстановился и преимущества
  кандидата нет — НЕ переключать.
- (validated ∩ solved)/S ≥ 95%; V/A и доля validated-clearance на рун — каждое не более
  чем на 5 п.п. ниже контроля; validated-clearance на рун у кандидата ≥ 85%; 0 невалидных
  решений, переданных в запросы.
- Задержки: p95 (nearest-rank) по всем попыткам ≤ 120 с и ≤ 1.20× контроля (неудачи
  включены); p95 (nearest-rank) успешной валидации ≤ 100 с.
- Публиковать все счётчики и неопределённости. Успех пилота — не универсальное
  каузальное доказательство.

### 3.4. Другие потребители общего стека

Реальные общие потребители (WhoScored и SoFIFA; добавить любого дополнительного
потребителя, найденного на preflight) остаются на общем стеке. Гейты: 0 запросов/сессий
других источников к кандидату; 0 изменений digest/конфигурации общего стека; 0 новых
OOM/рестартов общего стека. Только естественный существующий трафик; сравнимые
baseline/канарейка UTC-окна при неизменных версиях/конфигурации: у каждого источника
≥ 30 запросов в каждом окне; рост доли ошибок ≤ 2 п.п. и p95 задержки ≤ 1.10× базовой
линии. Никогда не маршрутизировать других потребителей на кандидата ради изготовления
выборки; недостаточность выборки — inconclusive. FBref не использует FlareSolverr в
предоставленной архитектуре; не выдумывать для него прямой эффект кандидата.

### 3.5. Останов и откат

Останов: любое нарушение маршрутизации/гард/квот, OOM/рестарт общего стека,
квалифицирующая регрессия другого источника или 5 последовательных рунов кандидата без
validated clearance.

План отката: прекратить новые назначения кандидата; восстановить заранее сохранённую
ClubElo-маршрутизацию на контроль и сверить контрольную сумму; закрыть сессии/lease
кандидата; сохранить санитизированные свидетельства; остановить/удалить только
изолированного кандидата; проверить неизменность идентичностей общего
контейнера/образа/конфигурации. Не печатать исполняемые производственные команды.
Сам откат дополнительно требует отдельного одобрения и окна владельца.
