# SQL-клиент мониторинга

`scripts/ops/trino_monitor_ro.py` — подготовленная замена отсутствующего общего
`/root/.claude/bin/trino-ro.sh`. Установка не входит в авто-доставку ClubElo.

Интерфейс: один аргумент SQL, CSV без заголовка с кавычками у всех полей, NULL как
пустое поле. Пустой результат и ошибка дают exit 1 без частичного CSV; отказ
валидатора — exit 2. SELECT/WITH и объединения SELECT разрешены, несколько
statements, операции записи, неизвестные/пользовательские функции и connector
table functions запрещены. Поддержан только полный синтаксис
`SHOW TABLES FROM catalog.schema [LIKE 'pattern']` для существующих fallback.
DESCRIBE и остальные SHOW не поддержаны: текущие потребители их не используют.
`to_iso8601` явно разрешён как встроенная функция Trino, которую sqlglot
представляет неизвестной функцией. Это намеренно ограниченный
интерфейс, не полная копия утраченного оригинала.

Хостовый Python должен иметь уже используемый проектом sqlglot (проверена 30.12.0
из requirements-ci.txt). При отсутствии валидатора клиент отказывает до Docker.
SQL проверяет AST Trino; неподдерживаемые команды отклоняются без записи SQL в лог.
Потребителей с отвергнутыми функциями проверять отдельно, не ослаблять gate ради
зелёного результата. Правила доступа самого Trino остаются дополнительной границей.

Транспорт использует существующий `airflow-scheduler`, его окружение и пакет
trino. Пароли не читаются на хосте и не выводятся. Python запускается с `-B` из
`/tmp`; изменения mounted-кода, cron и контейнеров не нужны. TLS-параметры
повторяют существующий транспорт morning_report. HTTP timeout — 30 секунд без
повторов, серверный query_max_run_time — 840 секунд, внешний timeout — 870 секунд.
Это оставляет запас перед C1_SQL_TIMEOUT_S=900 в morning_report и допускает
документированный запрос C1 длительностью около 280 секунд. Более короткие
таймауты потребителей (60–600 секунд) сохраняются: они могут прекратить ожидание
раньше, но оставшийся серверный запрос ограничен 840 секундами. HTTP timeout
относится к одному запросу протокола, а не общей длительности SQL.
После убийства Docker-клиента серверный лимит ограничивает оставшийся запрос.

Перед ручной установкой общего runtime-компонента нужны разрешение соответствующего
объёма, независимое ревью и проектные проверки. Установить проверенную фиксированную
версию и совместимый shim по прежнему пути, использующий явный Python с sqlglot.
Зафиксировать SHA256, владельца, права и отсутствие прежнего файла; если файл уже
появился, не перезаписывать чужую доставку. Откат возвращает сохранённый файл либо
удаляет только установленный этой доставкой shim при совпадении hash.

После разрешённой установки: SELECT 1, sentinel/NULL CSV, SELECT с заведомо пустым
результатом, затем read-only SQL ClubElo. Отдельно проверить потребителей остальных
источников. Полный morning_report для smoke не запускать: он имеет внешние побочные
действия. Доставка клиента не доказывает восстановление мониторинга без этих проверок.

Изолированные проверки (без Docker и production):

```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 /root/.venvs/dpf-test/bin/python -B -m pytest tests/unit/scripts/test_trino_monitor_ro.py -q
```
