# SofaScore: сторож актуалки и истории (#1361)

Код готовится к отдельной установке на хост. PR ничего не меняет в cron,
runtime, шлюзах или Airflow. Сторож не запускает сбор, не снимает паузы и
не отправляет Telegram-уведомления. Merge не закрывает #1361: после установки
нужны три суток без ложных тревог.

## Числа и правила

- #1355: сохранённый итог вчерашних суток из `daily.jsonl`, без нового Trino-замера
  и изменения знаменателя. Ядро <99% ≤24 ч — событие `refresh:coverage`.
- #1356: SQL и строка `sofascore_red_share` из того же дерева, что сторож.
  Общая строка совпадает со сводкой; отдельно проверяется каждая полоса, чтобы
  большой зелёный поток актуалки не скрывал историю. Красных TI ≥20% — событие.
  Только терминальные mapped `run_*_scope`, без удвоения валидаторами/DagRun.
- #1360: существующие SQL, обработка прошлых попыток и verdict
  `sofascore_pool_wait`. Событие при ожидании либо занятии пулов дейли;
  интервалы планировщика ≤60 с и retry_delay не превращаются в ожидание.
- Закрытые матчи истории: `matches_complete` успешных отчётов, один раз на
  `(run_id, scope_digest)`; число публикаций, не уникальных новых матчей кампании.
  `capture_status_rows` не доказывает закрытие. Порог темпа ≥10,1 тыс./сут
  относится к волне 2 и этим PR не включается.
- При подтверждённой работе без продвижения либо платных запросов ≥6 ч — событие.
  `request_count` берётся из отчётов capture; время отчёта — консервативная верхняя
  граница времени активности. Байтовые чанки журнала не считаются запросами.
  Для явного saved-raw work `source_work_expected=false` исключает тревогу о платных
  запросах. Пропавшие/битые отчёты дают неизвестную метрику, не ноль.
- Необъяснённая пауза/нулевой пул при наличии работы ≥15 мин — событие `stop`.
  История считает оставшуюся очередь wave 1 (включая парковку, год ≤2025).
  Актуалка проверяет незавершённые задачи и пропущенный запуск по расписанию
  `30 0,8,15 * * *` с 15-минутным запасом планировщика.

Суточные правила готовы с 05:00 UTC (08:00 МСК). Нулевой знаменатель,
нет терминальных TI, старые/отсутствующие результаты — `unobservable`, без
«всё хорошо». Другие доступные метрики продолжают проверяться. Неверное,
будущее или старше 30 минут наблюдение целиком отклоняется; состояние не заменяется.

## Паузы и события

Для `--collect` обязательно указать отдельный JSON-файл политики `--pauses`.
Пустой список `[]` означает отсутствие согласованных пауз. Запись содержит
`lane` (`history`, `refresh`, `daily`), `start`, `end`, `reason`, `approval`.
Для бессрочной паузы `end=null` и `indefinite=true`; `approval` — ссылка на
конкретное решение владельца. Сам флаг Airflow `is_paused` не является разрешением.
Для текущей истории при будущей установке внести действующее разрешение из
актуального handoff; изменение/снятие паузы — отдельная операция владельца.

Пауза объясняет только свою полосу. Суточное отклонение подавляется только
если согласованные интервалы покрывают весь день измерения. Пауза истории
не скрывает покрытие актуалки; для покрытия должны быть приостановлены
`refresh` и `daily`. Числа продолжают печататься без изменения.
После паузы отсчёт тишины начинается заново. Свежий маркер `sofascore-inflight`
оправдывает delivery не дольше 3 ч; один час суток сам по себе не оправдание.

Эпизод сохраняется через паузу, недоступную метрику, рестарт и смену даты.
Он завершается только подтверждённым нормальным результатом. Один эпизод —
одна issue с классом, полосой, датой начала UTC и доказательствами. В issue
нет команды unpause, выдуманной причины или «допиши». State сохраняется до
внешнего запроса, запись атомарная с fsync; один процесс держит flock.
После таймаута GitHub точный маркер сверяется через paginated REST среди
открытых и закрытых issue. Факт попытки POST сохранён заранее; пока результат
не определён, разрешён только поиск. Отсутствующий маркер не доказывает, что
POST не завершится позже, поэтому второй POST автоматически не отправляется.
Если issue так и не найдена, нужна отдельная сверка исхода попытки владельцем,
а не сброс state. Ручное закрытие не создаёт повтор. Добавление в
Project Data Platform №2 повторяется отдельно; сбой не создаёт вторую issue.
Неподтверждённые события сохраняются даже после восстановления полосы.
Повреждённый state не обнулять: восстановить сохранённую копию и сверить маркеры.

## Проверка без внешних операций

Из своей development-копии:

```bash
python scripts/research/replay_sofascore_watchdog.py \
  --snapshots-output /path/to/task/history.jsonl
python deploy/sofascore/pipeline_watchdog.py \
  --replay /path/to/task/history.jsonl --state /path/to/task/replay-state.json
```

Replay не вызывает subprocess, Docker, Trino, GitHub или SofaScore. Для каждого
суток 14–17.09 сохранённые TI дают тревогу; весь период 14–22.09 даёт одну
продолжающуюся issue-кандидат. Происхождение данных — README рядом с fixture.
Отсутствующие сентябрьские метрики не выдумываются.

`--snapshot` читает один JSON, `--replay` — JSONL. Обязательные поля:
`observed_at` (timestamp с поясом), `day` (сутки UTC). Необязательные:
`coverage` (исходная запись #1355), `red_share` (DAG → `[failed,total]`),
`pool_wait` (поля `PoolWait`), `lanes` (history/refresh → наблюдение), `evidence`.
Наблюдение полосы: `expected_work`, `demand_since`, `closed`, `last_progress`,
`last_paid`, `daily_closed`, `delivery_since`, `source_work_expected`.
Отсутствующий счётчик означает неизвестность; явный null в `last_*` — достоверно
не было активности. `--now` нужен для фиксированных одиночных fixtures.
Dry-run по умолчанию пишет **только свой state**, поэтому никогда не проверять
на state установленного сторожа. Replay и publication несовместимы.

## Последующая установка — отдельно

После разрешения установки выбрать приватный постоянный state, сверить
дерево/модули с SHA релиза, политику пауз, runtime-пути и расписание актуалки.
Заменить старый `sofascore_stall_watch.py` одним экземпляром нового сторожа;
не оставлять оба активными. Не менять lease-watchdog: это другой процесс.
Первый запуск — `--collect --dry-run` с отдельным state. Collector делает только
ограниченные SELECT в dedicated metabase и чтение локальных файлов, без Trino
и без вызова измерителя #1355. Собирать ожидаемые и реальные события для
трёхсуточной приёмки; разрешение уведомлений/issue publication оформить отдельно.

Публикация включается только `--collect --publish-issues --pauses POLICY --state STATE`.
Она запрещена с replay, snapshot, подменой времени или dry-run. Процесс не должен
запускаться из deployment-дерева с записью Python bytecode: использовать
`PYTHONDONTWRITEBYTECODE=1`. Доставка/регистрация cron в этот PR не входят.
