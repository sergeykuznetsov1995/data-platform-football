# Приёмки задач: журнал, handoff и Miro

Применяется только к Football. Решения владельца от 09.10.2026 сохранены в `docs/decisions/PARSER-ACCEPTANCE-GRILL-2026-10-09.md` и комментарии https://github.com/sergeykuznetsov1995/data-platform-football/issues/1142#issuecomment-6080753113.

Последнее уточнение владельца от 09.10.2026 заменяет ежедневное обновление: Miro обновляется после завершения задачи по источнику, перед итоговым ответом, без отдельной просьбы. Обновление при явном handoff сохраняется. Таймер `parser-acceptance-process` остановлен; возобновлять его ради ежедневного обновления нельзя.

У задачи одна запись приёмки. Следующая разработка не заменяет эту запись. День зелёный только по доказанному результату. Новая выкладка сохраняет незатронутые приёмки и начинает новую серию затронутых. Новая ошибка вне уже порученного исправления означает разбор и уведомление, а не автоматическую правку кода.

## Установленные пути

- Код: `/root/data-platform-football/.local/acceptance/runtime/` — проверенная копия выпуска; `manifest.json` фиксирует ревизию и хеши. Наличие этого пути само по себе не доказывает установленную/принятую версию.
- Журнал: `/root/data-platform-football/.local/acceptance/state/acceptance.sqlite3`.
- Копии доказательств: `/root/data-platform-football/.local/acceptance/state/evidence/`.
- Pending Miro: `/root/data-platform-football/.local/acceptance/miro-acceptances.json` и `miro-sources.json`.
- Обменные файлы и протокол проверок: `/root/data-platform-football/.local/tasks/parser-acceptance-process/`.
- Существующий обзор: https://miro.com/app/board/uXjVEfZMz1U=/?moveToWidget=3458764685876111831.
- URL таблицы отдельных приёмок хранится в `/root/data-platform-football/.local/acceptance/installation.json` после фактического создания и readback.

Область `.local/` не хранится в Git. Перед обновлением выпуска сохранить резервную копию SQLite штатным `sqlite3.Connection.backup()` и evidence вместе с manifest; копирование открытого файла БД не заменяет backup. Не удалять журнал при уборке worktree.

## Регистрация

Ведущий читает полный актуальный текст issue, критерии источника и действующие решения владельца. Хеш `issue_body_sha256` — SHA-256 точного UTF-8 текста GitHub body, без удаления пробелов и переносов. Все обязательные критерии представлены в `criteria`, включая разовые и производственные проверки. Список ссылок или одно зелёное выполнение DAG не заменяют эту работу.

Запись имеет `id=source-issue`, например `fotmob-1288`, `source`, `issue`, `title`, `issue_body_sha256`, `definition_confirmed`, `started_at`, `deployed_revision`, `criteria`. До проверки полного определения: `definition_confirmed=false`. До доказанной доставки и корректного начала окна: `started_at=null` и `deployed_revision=null`. При импорте старых handoff эти поля нельзя заполнять датой merge.

Критерий: `id`, понятный `title`, `kind=days|runs|check`, `required` и `min_samples`. Для `days` также `period_seconds`; 86400 означает полные 24 часа от `started_at`. Граница берётся из критерия источника: для UTC-суток начало ставится в подходящие 00:00 UTC, а не в момент произвольного запуска проверки. Если критерий требует отдельной начальной квалификации, сначала доказать её. Дни без материала не считать успехом по умолчанию. Агрегат за 72 часа, контроль «на третьи сутки» и сценарий теста «через 7 дней» не превращать в три или семь успешных дневных точек.

Для PR с незавершённой runtime-проверкой: `reference_kind=pull`, `issue=null`, `pull_request=N`, `id=source-pr-N`, `reference_url` с точным URL PR, `auto_close_issue=false`. Хеш относится к полному body PR. Такая приёмка не закрывает и не переоткрывает связанные issue/эпик. Связи и ограничения сохраняются в `metadata`.

```bash
python3 /root/data-platform-football/.local/acceptance/runtime/scripts/acceptance.py \
  --state /root/data-platform-football/.local/acceptance/state \
  register --input /root/data-platform-football/.local/tasks/parser-acceptance-process/spec.json
```

При повторной регистрации того же определения запись не меняется. Изменённые критерии оформляются через `revise --id ... --input ...`: `{spec, expected_revision, reason, evidence}`. Старые определения и результаты остаются в истории, новая серия начинается без переноса прежних зелёных точек. Это техническая операция внутри ранее разрешённого объёма; она не позволяет отменить ограничения владельца. `metadata.close_hold=true` блокирует закрытие.

## Результат проверки

Вход `observe --id source-number --input report.json`:

```json
{
  "series": 1,
  "criterion": "freshness",
  "key": "2026-10-10T00:00:00Z",
  "ordinal": 0,
  "start": "2026-10-10T00:00:00Z",
  "end": "2026-10-11T00:00:00Z",
  "checked_at": "2026-10-11T00:05:00Z",
  "status": "unknown",
  "samples": 0,
  "reason": "Нет итогового измерения за весь интервал",
  "evidence": []
}
```

Это пример формата, не действующий результат. `key` для прогонов — фактическая идентичность запуска, `ordinal` — его место в последовательности ожидаемых проверок. Нельзя перенумеровать прогоны, выбросив провал или пропуск. Для дней ordinal вычисляется относительно точного начала серии. Для разовой проверки ordinal=0.

`pass` и `fail` требуют непустых файлов доказательств, относящихся к конкретному интервалу, версии, выборке и критерию. Журнал сохраняет копию и хеш файла. Разрешены доказательства внутри Football; выбранные доказательства из legacy-путей сначала сохранить в каталоге задачи, очистив от секретов. Не передавать содержимое credentials. Коннектор Miro получает сводку и ссылку на задачу, а не сырые файлы.

Неизвестный результат можно восстановить по сохранённым данным. Нельзя заменить реальный провал зелёным днём: после необходимого исправления начинается новая серия. Если между успешными днями пропуск, они не склеиваются. Отсутствие доказательств само по себе не устанавливает дефект парсера.

Движок проверяет последовательность, интервалы, наличие доказательств и все критерии. Смысл измерения сверяет ведущий: наличие JSON-файла не доказывает его вывод. Для старта, изменения версии или зависимости используется `change`: `{expected_series, expected_revision, impact: affected|unaffected|unknown, deployed_revision, started_at (affected), reason, evidence}`. Обе ожидаемые версии брать из `show` перед оценкой влияния; при конфликте перечитать факты, не подставлять новый номер в прежний вывод. При `unknown` закрытие удерживается до разбора влияния.

## Завершение задачи и каждый handoff

После выполнения и проверки порученной задачи по источнику выполни шаги ниже **перед итоговым ответом**. Не жди отдельного вызова `$handoff`, переключения чата или истечения суток. Укажи, что именно завершено: разработка, доставка или полная приёмка. Если разработка закончена, а нужны ещё 3–7 дней проверки, источник остаётся на приёмке; обновление доски не закрывает issue и не создаёт успешных дней.

Это обновление существующей сводки как часть завершения задачи, а не отдельное поручение на передачу чата. Явный handoff запускает те же шаги. Промежуточный ответ о ходе работы не означает завершения задачи. При недоступности Miro сохрани результат и pending, сообщи об отказе публикации; не утверждай, что доска обновлена.

1. Сохранить обычный текущий handoff источника. Сохранить в нём ссылки на все незавершённые приёмки и существующее наблюдение. Не присваивать чужой watcher и не останавливать его из-за новой задачи.
2. До чтения handoff получить snapshot журнала и сохранить `handoffs[source].revision` как `expected_revision` (0 для первой записи). Подготовить структурированную сводку: `source`, `expected_revision`, `path` на копию handoff внутри каталога задачи, `checked_at` времени подтверждённого факта, `summary`, `done`, `next_step`, `status` из существующих значений Miro. Отдельные времена проверок можно пояснить текстом. `recorded_at` журнал назначает сам. Старые факты не датировать временем сохранения handoff. Перед записью сверить SHA исходного handoff с прочитанным; при изменении документа или конфликте revision перечитать его и заново составить сводку.
3. Выполнить `acceptance.py --state ... handoff --input summary.json`. Другие приёмки источника сохраняются. Этот шаг не записывает успешный день и не подтверждает новую production-проверку.
4. Получить snapshot с `--sources <runtime>/configs/acceptance/sources.yaml`. Обновить соответствующую строку обзора в Miro по процедуре ниже; при изменении приёмок обновить и их таблицу. Не писать таблицу напрямую в обход общей очереди публикации.
5. Сохранить readback или явное состояние «синхронизация ожидает повтора». Успешное сохранение документа не означает успешную публикацию.

Режим `наблюдение` допускает эти отчётные записи и закрытие после полной приёмки в разрешённых границах. Он не разрешает новый ремонт, перезапуск сборщика, доставку или изменение квот.

## Публикация Miro

`acceptance_miro.py` не имеет отдельного доступа к Miro. Внешние вызовы выполняет ведущий через уже подключённые инструменты Miro. Нельзя искать токены, добавлять OAuth или менять права для обхода отсутствующего коннектора.

1. Сохранить полный результат `table_list_rows` нужной таблицы, включая все страницы. Одна страница с ненулевым cursor не считается полным снимком. Использовать `structuredContent` результата, либо декодировать JSON текстового блока. Не сохранять дублирующую оболочку MCP вместо результата.
2. Сохранить snapshot журнала. `generated_at` — время представления; `checked_at` остаётся временем факта.
3. `prepare --snapshot snapshot.json --remote rows.json --table-url URL --state STATE` сохраняет pending план до отправки. Для обзора источников добавить `--mode sources`, использовать отдельный STATE и URL обзора.
4. Прочитать план. Пустой `rows` подтверждается `ack` по имеющемуся readback. Для непустого выполнить `dispatch --plan-id TOKEN --state STATE` непосредственно перед внешним вызовом.
5. Вызвать `table_sync_rows` с точными `miro_url` и `rows` плана. Сохранить ответ, затем заново прочитать полную таблицу.
6. `ack --plan-id TOKEN --remote after.json --state STATE` подтверждает только совпадение нужных строк и ячеек. После ack новый snapshot может публиковать следующую ревизию.

Если исход запроса неизвестен, pending не снимается по возрасту. Сначала прочитать таблицу и выполнить `reconcile --plan-id TOKEN --remote after.json --state STATE`. Найденная строка переиспользует rowId. Пропавшая новая строка после неоднозначной вставки не разрешает слепую повторную вставку. `resolve --retry-missing-inserts --resolution-evidence FILE` применим только с доказанным завершением прежнего запроса без записи; требования точных аргументов см. `--help`. Неотправленный prepared план можно отменить `abandon`; dispatched план так не снимается.

На одну таблицу — один pending план; SQLite-журнал при этом может получать новые результаты. Старый export не должен затирать новую подтверждённую публикацию. Ссылки и времена не выдаются за новую проверку. Чужие строки и колонки не удаляются.

## Результаты приёмки при завершении задачи

Отдельной ежедневной проверки для обновления Miro больше нет. При завершении порученной задачи или проверки используй уже полученные измерения за нужный интервал: `show --id`, актуальный полный критерий, версия и доказательства. Результаты запиши через `observe`, затем опубликуй затронутые приёмки вместе со сводкой источника. Если новых доказательств нет, сохрани прежние результаты и исходное время проверки.

Если определение ещё не квалифицировано, подтверждай его только по полным доказательствам через `confirm-definition`; начало серии фиксируй через `change` по реальной доставке и правилам источника. Неизвестное остаётся неизвестным. Новые сборщики, доставка и снятие hold этим шагом не разрешены. Новая ошибка требует разбора и уведомления; новый ремонт требует поручения.

Существующие наблюдения источников и расписания парсеров продолжаются по своим правилам. Не присваивай их и не останавливай ради отмены ежедневной публикации. Само течение времени и промежуточный статус в чате не вызывают публикацию и не засчитывают успешный день.

## Закрытие

1. Повторно прочитать GitHub body/state и все внешние условия/ограничения задачи. Вычислить body hash. При расхождении определения нельзя закрывать по старой схеме: нужен разбор и `revise` с новыми доказательствами.
2. Выполнить `prepare-close --id ... --body-sha256 ...`. Команда проверяет все критерии и доказательства, сохраняет token и точную ревизию. Она сама не закрывает GitHub.
3. Подготовить итоговый отчёт со ссылками на доказательства и уникальным маркером token. До повторной публикации проверить существующий комментарий с этим маркером. Опубликовать его один раз и закрыть точную issue штатным `gh issue close` без закрывающих ссылок на другие задачи. Перед действием заново убедиться, что план и все критерии актуальны.
4. Прочитать состояние issue и комментарий. `confirm-closed --input ...` принимает `{token, receipt:{issue,state:"CLOSED",body_sha256,report_url}}`. Если внешний ответ потерян, сначала прочитать GitHub, не публиковать отчёт повторно.
5. Для `auto_close_issue=false` сохранить локальный финальный отчёт и подтвердить `{token, receipt:{state:"ACCEPTED",body_sha256,evidence:[path]}}`. Связанные GitHub issue и PR остаются в прежнем состоянии.
6. Обновить Miro и уведомить владельца. При отказе одного шага продолжить с фактического состояния, сохранив pending, а не выдавать частичное выполнение за завершение.

## Проверка и восстановление

Затронутые тесты: `pytest tests/unit/scripts/test_acceptance.py tests/unit/scripts/test_acceptance_miro.py -q`. Полный `tests/unit` обязателен для изменений кода перед PR по правилам проекта. Изменение только инструкций проверяется содержанием, ссылками и поведением в свежем контексте. Реальный тест владельца: завершить задачу в существующей сессии FotMob без просьбы обновить Miro и без `$handoff`; до итогового ответа должны быть сохранены результат и подтверждённая публикация. Наличие инструкции не считается прохождением этого теста.

Журнал можно прочитать командами `snapshot`, `show --id` и `history --id`. Не редактировать SQLite/pending вручную, не удалять старую серию и не снимать чужие блокировки ради зелёного результата. Если установленный runtime/manifest не совпадает, остановить только публикацию этого механизма и подготовить проверенный выпуск; source-процессы продолжают существовать независимо.
