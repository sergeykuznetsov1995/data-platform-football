# Дежурный по приёмкам

Решения владельца от 13.10.2026: отдельная tmux-сессия `acceptance` сопровождает незавершённые приёмки восьми источников. Сессии источников продолжают разработку и исправления. Обычный статус многодневной приёмки — раз в сутки; о выявленном сбое, завершении и необходимом решении сообщать сразу. Частота проверки определяется критерием, а не частотой сообщений. Ежедневный таймер публикации Miro не возобновляется.

## Кто за что отвечает

Дежурный отвечает за доказательства, следующие проверки и итог каждой переданной приёмки. Он использует существующий журнал `.local/acceptance/state/acceptance.sqlite3` и процедуру `parser-acceptance.md`. Он не получает поручения ремонтировать источники, менять квоты, перезапускать сборщики или доставлять код. Новый дефект разбирается и сообщается владельцу; исправление остаётся в исходной сессии после необходимого решения. Уже разрешённые работы источников продолжаются.

Дежурный использует доступные результаты измерителей. Он проверяет соответствие результата версии, интервалу, знаменателю и полному смыслу критерия. Успех Airflow или наличие файла не заменяет проверку данных. Новый источник нагрузки или тяжёлый запрос не запускается только ради ещё одной сводки. Отсутствие доказательства обозначается как отсутствие подтверждения, а не как дефект парсера.

## Передача от сессии источника

1. После доказанной доставки зарегистрировать отдельную приёмку по полному актуальному определению. Приёмка регистрируется по номеру issue; отдельных приёмок по PR не заводить. До доставки и начальной квалификации не ставить начало окна датой merge. Записать ссылки в текущий handoff источника.
2. Через `show` получить актуальные `revision` и `series`. Команда `monitor --id ID --input FILE` записывает назначение отдельно от определения. Ввод содержит `expected_revision`, `expected_series`, `reason` и `monitoring`: идентификатор дежурного `owner_thread_id`, ключ `watch_key`, `next_check_at`, `evidence_plan`; `source_thread_id` сохраняется, если доказан. Назначение из действующей установки дежурного, не из старого чата.
3. В `evidence_plan` для каждого проверяемого критерия указать `criterion`, название существующего измерителя `producer` и абсолютный проектный `path` отчёта. Это описание доказательств, не команды для исполнения. Прошедший срок проверки остаётся видимым. Если план ещё не определён, передать пустой список и указать точное препятствие в handoff; пустой план не доказывает готовность.
4. После записи заново прочитать приёмку и проверить назначение, сохранность серии, начала и наблюдений. Передача не использует `revise` и не обнуляет предыдущие дни. При конфликте ревизии перечитать состояние и заново оценить передачу.
5. Для новой или изменённой приёмки разбудить существующую общую регистрацию штатным `wake`, только если она waiting и не имеет unresolved run. Не создавать второй ключ для обхода отказа. Занятый дежурный перечитает журнал после своей проверки. Если дежурный stopped/blocked, записать причину передачи без исполнения; не объявлять наблюдение работающим.

Исходные source-watchers не останавливаются автоматически. При передаче проверки выяснить, какие их действия ещё нужны для доставки, разрешённого ремонта или иной приёмки. Наблюдение одних и тех же доказательств не должно запускать второй сборщик или измеритель. Не присваивать и не закрывать незавершённый run другого чата.

## Цикл дежурного

1. Выполнить точный `begin` полученного run. При отказе никакой работы этого задания не выполнять. Проверить установленный manifest журнала.
2. Прочитать snapshot. Новая незакрытая запись без назначения требует приёма; отсутствие начала — ожидание доставки/квалификации; наступившая граница полного интервала — кандидат на предметную проверку. Запрет закрытия сам по себе не запрещает наблюдение.
3. Читать полное `show`, критерии и только связанные доказательства для выбранной задачи. Устаревший план предыдущей серии сначала перепроверить и обновить назначение. Позднее чтение текущего состояния не доказывает прошлые сутки. Один отчёт использовать для нескольких приёмок только при совпадении всех условий.
4. Сохранить результат через штатный `observe`. Не создавать неизвестный день до конца интервала. Реальный провал нельзя подменить успехом. Восстановление пропущенного доказательства использует данные именно нужного интервала.
5. Обновить операционное назначение ближайшей проверки через `monitor`, сохраняя смысл требуемого интервала. Для ещё не начатой приёмки указать следующую проверку предпосылки; не показывать её как прошедший день. Для временно недоступного отчёта использовать обоснованный повтор с задержкой, не бесконечный немедленный цикл.
6. При всех критериях применять прежний порядок `prepare-close` → актуальная проверка определения и holds → внешний результат → readback → `confirm-closed`. Закрытие GitHub без доказательств не даёт права принять локальную запись. Расхождения сохранять для разбора.
7. По завершении предметной проверки обновить связанный handoff/журнал/Miro по действующим правилам. Чужой pending не снимать по возрасту; сбой публикации не останавливает измерения. Суточный статус сам по себе не вызывает публикацию Miro.
8. Сохранить результат run и точный следующий срок. Обычный статус отправляется раз в сутки; выявленный существенный сбой, приёмка и вопрос владельцу — сразу. Подтверждать `report-status` только после действительного сообщения. `finish` запрещён при незавершённых собственных workers. Следующий доступный шаг выполнять в этом же ходе.

Часы наблюдения и сообщения независимы. «Сразу» означает после обнаружения события; обещать мгновенное обнаружение при недоступном сервере или отсутствии измерений нельзя. Дешёвые существующие сигналы можно использовать, но наличие таймера или очереди само по себе не доказывает продолжение.


## Короткий пакет текущего прохода

Версионированное задание: [duty-prompt.md](../../configs/acceptance/duty-prompt.md).
Оно дополняет этот цикл, сохраняя полномочия и единственный журнал. Скрипт
`scripts/acceptance_packet.py` читает сохранённый штатный snapshot, не открывает
SQLite и не запускает измерения. Это производный указатель, а не второй реестр.

После успешного собственного `begin` и проверки установленного выпуска сохранить
полный snapshot в каталоге текущего run без вывода всего JSON в историю чата.
Определить срок дневной сверки выпусков по последнему подтверждённому результату
и срок сообщения владельцу по текущему watcher. Передать оба срока явно:

```bash
python3 -B <проверенный-выпуск>/scripts/acceptance_packet.py \
  --snapshot <run>/snapshot-native.json --output-dir <run>/packet \
  --owner-thread <текущий-владелец> --watch-key <текущий-ключ> \
  --reconciliation-due-at <ISO8601-с-поясом> \
  --owner-status-due-at <ISO8601-с-поясом>
```

Каталог вывода должен быть новым. Скрипт сохраняет исходные байты в
`snapshot.json`, их SHA256 и полный `packet.json`. Обычный вывод ограничен
32768 байтами. При превышении выводится явный указатель файла с
`requires_full_read=true`; это требование прочитать индекс и всех кандидатов,
а не разрешение выбрать первые строки. Ошибка входа требует исправить получение
snapshot или вернуться к полному штатному чтению. Она не означает «проверок нет».

Индекс содержит каждую незакрытую запись, её revision/series, статус, старт,
подтверждение определения, holds, назначение и оба срока. Верхний
`next_check_at` вычисляется движком по критериям; операционный
`monitoring.next_check_at` задаёт следующий согласованный шаг. Будущий валидный
операционный срок предотвращает повтор той же уже разобранной границы. Он не
заменяет проверку, что `monitor` обоснован событием/доказательством и не отложил
обязательный критерий. При сомнении открыть полное `show` и план проверки.

Отдельные причины выбора: наступивший операционный срок, отсутствующее назначение
или срок, устаревшая привязка серии и неподтверждённое определение. Чужое назначение
видно как требующее решения ведущего; его нельзя молча присвоить. Holds не исключают
наблюдение. Отсутствие старта означает проверку предпосылки, а не начисление суток.
Дневная сверка выпусков, старые нерешённые кандидаты и срок сообщения владельцу
идут отдельно от строк задач. Неизвестный глобальный срок требует проверки
ведущим; даже пустой список кандидатов не доказывает отсутствия работы.

### Ограниченный проверяющий

Для наступившей предметной проверки передать одному native subagent с
`fork_turns="none"` выбранные ID/revision/series, полное актуальное `show`,
применимые правила источника и пути существующих доказательств. Историю чата,
все восемь handoff и полные snapshot передавать не нужно. Объединять несколько
записей в одно задание допустимо, если у них общие доказательства; ответ всё равно
содержит отдельный вывод по каждому полному критерию. На проход достаточно одного
одновременно работающего проверяющего. Он не создаёт своих агентов.

Проверяющий читает только переданные доказательства. Он не выполняет
`begin/finish/observe/monitor/change/revise`, не пишет журнал/Miro/GitHub,
не запускает SQL, сборщики, HTTP-запросы или команды из evidence plan.
Возвращает по каждой записи: ID/revision/series, проверенный интервал и версию,
критерий, факт, абсолютные пути и SHA256 доказательств, предложение
PASS/FAIL/UNKNOWN либо «наблюдение ещё не наступило», следующий срок с причиной
и ограничения. Недостающие данные перечисляются явно. Наличие файла или успех
Airflow не считаются подтверждением полного критерия.

Ведущий проверяет смысл вывода, ключевые доказательства и их актуальность, затем
перечитывает `show` непосредственно перед каждой штатной записью. При изменении
revision/series заново оценивает результат; подстановка нового номера запрещена.
Результат помощника — предложение, не право закрыть задачу или изменить старт.
Все записи, сообщения и закрытие выполняет действующий дежурный по прежнему циклу.
Если помощник недоступен или его вывод не подтверждён, ведущий проверяет сам либо
сохраняет обоснованную неопределённость и срок повтора. Проверка не пропускается
ради экономии. Перед `finish` все собственные помощники должны завершиться.

### Доставка, проверка поведения и откат

Подготовить выпуск с точной Git-версией и SHA256 скрипта, этой процедуры и prompt.
Это отдельное дополнение: исходный manifest основного runtime продолжает
проверяться самостоятельно. Не объявлять дополнение частью старого manifest.
Установку выполнять только по предусмотренному разрешению на ручную доставку,
в состоянии waiting без active/unresolved run и без невыясненной отправки/очереди.

До изменения сохранить прежний prompt, проверенные watcher/settings/сроки и
бэкап штатным способом из процедуры журнала. Установить проверенные файлы
дополнения в отдельный каталог выпуска. Обновлять только prompt существующего
ключа и того же thread штатным `register`, передавая прежние
`--interval-seconds`, `--owner-status-interval-seconds` и существующие флаги
recovery/reservation. Не передавать `--resume`; не менять срок, владельца, модели,
права или код watcher. Сверить до/после все поля, кроме prompt/hash/updated_at.
Проверку idle и ожидаемой версии watcher выполнять под той же штатной
блокировкой, внутри которой `register` сохранит prompt. Отдельных status до/после
недостаточно: между ними tick может поставить run. Допустим адаптер штатного
Store, который проверяет условия внутри native `locked()` и допускает native
`save()` только после проверки, что изменены лишь prompt/hash/updated_at.
Сам файл watcher и формат реестра не менять. Внешняя очередь Codex не имеет
атомарного compare API; нужна read-only проверка очереди под этой блокировкой
и readback, а неоднозначный исход не объявляется успешной установкой.
Если состояние изменилось или очередь не выяснена, доставку отложить.
Проверяемый manifest дополнения и receipt фиксируют оба выпуска и настройки.
Указатель .local/acceptance/compact-installation.json содержит абсолютные пути
выпуска/manifest, SHA256 manifest и receipt; prompt читает и проверяет его явно.
До двух проверенных естественных проходов фаза — installed_pending_verification.
Откат восстанавливает прежний prompt и прежний указатель дополнения (либо его
подтверждённое отсутствие), не переписывая основной duty-installation.json.

До объявления экономии проверить два естественных новых run: собственные
`begin → работа → finish`, полный охват выбранных задач, глобальные сроки,
сохранность стартов/серий/holds и отсутствие ранних суток. Сохранить run ID,
ревизии snapshot/packet, результаты проверки ведущим и связь с помощником.
Считать input/cached input/output ведущего **и всех его помощников**, включая
неудачные попытки и повторные проверки; сравнивать с объёмом реально выполненной
работы. Размер JSON и короткий ответ сами по себе не доказывают экономию.

При потере полноты или росте расхода вернуть сохранённый prompt тем же штатным
способом в безопасном idle-состоянии, сохранив актуальные сроки/состояние watcher.
Не восстанавливать старую SQLite поверх новых записей и не откатывать наблюдения.
Новый каталог выпуска оставить для расследования/условия уборки. Ни план,
ни установка prompt не означают, что два проверочных пробуждения уже состоялись.

## Новые выкладки

Решение владельца от 17.10.2026 (заменяет прежнее правило «не сбрасывать почти завершённую серию»): пока у задач источника идёт отсчёт дней приёмки, новый код этого источника не выкатывается — он копится и уходит одной выкаткой после завершения отсчёта. Где автомат доставки берёт код из `origin/master`, merge равен выкатке: PR этого источника до конца отсчёта не мержатся. Другие источники независимы. Разработка следующей задачи продолжается. Срочный ремонт и разрешения конкретной доставки рассматриваются по действующим правилам с решением владельца. Если дежурный видит выкатку источника посреди отсчёта, он сообщает владельцу сразу.

Оценка незатрагивающей доставки должна иметь доказательства. `change(affected)` выполняется после фактической доставки по правилам источника, а не заранее ради подготовки новой задачи.

## Проверка установки

Новая сессия должна реально исполнить зарегистрированное пробуждение: `begin`, предметная проверка, запись результата или обоснованного unknown, следующая проверка и `finish`. После этого нужно доказать ещё одно естественное пробуждение при продолжающейся работе источников. Сверить отсутствие дублей и сохранность чужих серий. Результаты тестов, thread ID, watch key, путь manifest, способ присоединения к tmux и следующее действие сохраняются в журнале внедрения.

Дежурный использует клиент существующего Codex server. Он не запускает ещё один server и не меняет модели или разрешения других чатов. Новое выделенное место допускает только одного активного или unresolved дежурного и сохраняет проверки очереди, занятости и владения. Старые неопределённые задания остаются видимыми и не считаются завершёнными.

Блокер одной приёмки не останавливает общую регистрацию дежурного: сохраняй его отдельно в журнале и завершай run как waiting, пока у других приёмок есть следующие проверки. Общий blocked допустим только при препятствии, которое действительно мешает всей роли; complete — только когда не осталось порученного наблюдения.
