# Дежурный по приёмкам

Решения владельца от 13.10.2026: отдельная tmux-сессия `acceptance` сопровождает незавершённые приёмки восьми источников. Сессии источников продолжают разработку и исправления. Обычный статус многодневной приёмки — раз в сутки; о выявленном сбое, завершении и необходимом решении сообщать сразу. Частота проверки определяется критерием, а не частотой сообщений. Ежедневный таймер публикации Miro не возобновляется.

## Кто за что отвечает

Дежурный отвечает за доказательства, следующие проверки и итог каждой переданной приёмки. Он использует существующий журнал `.local/acceptance/state/acceptance.sqlite3` и процедуру `parser-acceptance.md`. Он не получает поручения ремонтировать источники, менять квоты, перезапускать сборщики или доставлять код. Новый дефект разбирается и сообщается владельцу; исправление остаётся в исходной сессии после необходимого решения. Уже разрешённые работы источников продолжаются.

Дежурный использует доступные результаты измерителей. Он проверяет соответствие результата версии, интервалу, знаменателю и полному смыслу критерия. Успех Airflow или наличие файла не заменяет проверку данных. Новый источник нагрузки или тяжёлый запрос не запускается только ради ещё одной сводки. Отсутствие доказательства обозначается как отсутствие подтверждения, а не как дефект парсера.

## Передача от сессии источника

1. После доказанной доставки зарегистрировать отдельную приёмку по полному актуальному определению. До доставки и начальной квалификации не ставить начало окна датой merge. Записать ссылки в текущий handoff источника.
2. Через `show` получить актуальные `revision` и `series`. Команда `monitor --id ID --input FILE` записывает назначение отдельно от определения. Ввод содержит `expected_revision`, `expected_series`, `reason` и `monitoring`: идентификатор дежурного `owner_thread_id`, ключ `watch_key`, `next_check_at`, `evidence_plan`; `source_thread_id` сохраняется, если доказан. Назначение из действующей установки дежурного, не из старого чата.
3. В `evidence_plan` для каждого проверяемого критерия указать `criterion`, название существующего измерителя `producer` и абсолютный проектный `path` отчёта. Это описание доказательств, не команды для исполнения. Прошедший срок проверки остаётся видимым. Если план ещё не определён, передать пустой список и указать точное препятствие в handoff; пустой план не доказывает готовность.
4. После записи заново прочитать приёмку и проверить назначение, сохранность серии, начала и наблюдений. Передача не использует `revise` и не обнуляет предыдущие дни. При конфликте ревизии перечитать состояние и заново оценить передачу.
5. Для новой или изменённой приёмки разбудить существующую общую регистрацию штатным `wake`, только если она waiting и не имеет unresolved run. Не создавать второй ключ для обхода отказа. Занятый дежурный перечитает журнал после своей проверки. Если дежурный stopped/blocked, записать причину передачи без исполнения; не объявлять наблюдение работающим.

Исходные source-watchers не останавливаются автоматически. При передаче проверки выяснить, какие их действия ещё нужны для доставки, разрешённого ремонта или иной приёмки. Наблюдение одних и тех же доказательств не должно запускать второй сборщик или измеритель. Не присваивать и не закрывать незавершённый run другого чата.

## Цикл дежурного

1. Выполнить точный `begin` полученного run. При отказе никакой работы этого задания не выполнять. Проверить установленный manifest журнала.
2. Прочитать snapshot. Новая незакрытая запись без назначения требует приёма; отсутствие начала — ожидание доставки/квалификации; наступившая граница полного интервала — кандидат на предметную проверку. Запрет закрытия сам по себе не запрещает наблюдение.
3. Читать полное `show`, критерии и только связанные доказательства для выбранной задачи. Устаревший план предыдущей серии сначала перепроверить и обновить назначение. Позднее чтение текущего состояния не доказывает прошлые сутки. Один отчёт использовать для нескольких приёмок только при совпадении всех условий.
4. Сохранить результат через штатный `observe`. Не создавать неизвестный день до конца интервала. Реальный провал нельзя подменить успехом. Восстановление пропущенного доказательства использует данные именно нужного интервала.
5. Обновить операционное назначение ближайшей проверки через `monitor`, сохраняя смысл требуемого интервала. Для ещё не начатой приёмки указать следующую проверку предпосылки; не показывать её как прошедший день. Для временно недоступного отчёта использовать обоснованный повтор с задержкой, не бесконечный немедленный цикл.
6. При всех критериях применять прежний порядок `prepare-close` → актуальная проверка определения и holds → внешний результат → readback → `confirm-closed`. Закрытие GitHub без доказательств не даёт права принять локальную запись. Расхождения сохранять для разбора.
7. По завершении предметной проверки обновить связанный handoff/журнал/Miro по действующим правилам. Чужой pending не снимать по возрасту; сбой публикации не останавливает измерения. Суточный статус сам по себе не вызывает публикацию Miro.
8. Сохранить результат run и точный следующий срок. Обычный статус отправляется раз в сутки; выявленный существенный сбой, приёмка и вопрос владельцу — сразу. Подтверждать `report-status` только после действительного сообщения. `finish` запрещён при незавершённых собственных workers. Следующий доступный шаг выполнять в этом же ходе.

Часы наблюдения и сообщения независимы. «Сразу» означает после обнаружения события; обещать мгновенное обнаружение при недоступном сервере или отсутствии измерений нельзя. Дешёвые существующие сигналы можно использовать, но наличие таймера или очереди само по себе не доказывает продолжение.

## Новые выкладки

Перед обычной доставкой source-сессия проверяет влияние на незавершённые приёмки. Если изменение сбросит почти завершённую серию, сначала закончить приёмку, затем доставить новую задачу. Подтверждённый владельцем пример — шесть из семи дней. Точный общий порог не утверждён; не заменять это решение новым универсальным числом. Разработка следующей задачи продолжается. Срочный ремонт и разрешения конкретной доставки рассматриваются по действующим правилам.

Оценка незатрагивающей доставки должна иметь доказательства. `change(affected)` выполняется после фактической доставки по правилам источника, а не заранее ради подготовки новой задачи.

## Проверка установки

Новая сессия должна реально исполнить зарегистрированное пробуждение: `begin`, предметная проверка, запись результата или обоснованного unknown, следующая проверка и `finish`. После этого нужно доказать ещё одно естественное пробуждение при продолжающейся работе источников. Сверить отсутствие дублей и сохранность чужих серий. Результаты тестов, thread ID, watch key, путь manifest, способ присоединения к tmux и следующее действие сохраняются в журнале внедрения.

Дежурный использует клиент существующего Codex server. Он не запускает ещё один server и не меняет модели или разрешения других чатов. Новое выделенное место допускает только одного активного или unresolved дежурного и сохраняет проверки очереди, занятости и владения. Старые неопределённые задания остаются видимыми и не считаются завершёнными.

Блокер одной приёмки не останавливает общую регистрацию дежурного: сохраняй его отдельно в журнале и завершай run как waiting, пока у других приёмок есть следующие проверки. Общий blocked допустим только при препятствии, которое действительно мешает всей роли; complete — только когда не осталось порученного наблюдения.
