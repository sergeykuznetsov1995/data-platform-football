# FotMob Silver #2021: подготовка полного прогона

Код ограничения запуска не включает расписание и не разрешает production.
Перед полным прогоном нужны отдельное подтверждение владельца, завершение
склейки Bronze #1892/#1879 и исправленный #2096 с проверкой обеих категорий.
Пилот #2020 и merge PR #2159 не являются полной приёмкой.

## Допуск и доставка

Использовать изолированный FotMob по `fotmob-isolated-ceremony-free.md`.
Перед доставкой проверить фактические mounts и SHA; добавить новый
`dag_transform_fotmob_silver_v2` в разрешённый набор DAG только в согласованной
доставке. Проверить перечитывание в живой метабазе и отсутствие import errors.
Общий scheduler и чужие DAG не менять. `schedule=None` сохраняется до отдельного
подтверждения расписания. Единственный писатель — этот DAG; host-side пилоты и
ручные записи в его таблицы одновременно запрещены. `max_active_runs=1`,
`max_active_tasks=1`, autocommit, один координатор Trino и стабильные часы обязательны.

Все запросы production DAG проходят `AdmittedCursor`, включая bootstrap,
барьер читателей и переключение. Допуск 00:30 включительно — 02:45 исключительно
МСК. Перед каждым запросом проверяются часы и число чужих RUNNING: максимум 5.
Проверяющий запрос исключается по собственному маркеру; это требует видимости
**всех пользователей** в `system.runtime.queries`. Проверить эту видимость до
активации, не считать пустой видимый список доказательством свободного кластера.
У лимита нагрузки нет атомарной резервации: другой запрос может стартовать
сразу после проверки. Чужие запросы никогда не отменяются.

На запрос сохраняются `query_max_memory=2GB`, `query_max_total_memory=2GB`.
`query_max_run_time` обновляется перед запросом: не более 30 минут и целого
числа оставшихся секунд окна, с запасом пять секунд на установку таймаута.
Если установка съела запас, запрос не допускается. Последние пять секунд
окна новые запросы не начинаются. Это ограничение допуска и серверного времени,
**не гарантия физического коммита строго до 02:45**: задержка сети, проверки
таймаута и коммита требуют живой проверки. После границы новые запросы не
допускаются. При неизвестном результате публикации сначала прочитать
`iceberg.ops.fotmob_reader_state` и сопоставить revision/updated_by с run_id.
Не запускать новую сборку до установления результата. До подтверждения поведения
на настоящем Trino полное исполнение нельзя объявлять безопасно принятым.

## Полная сборка и возобновление

В DAG оставить полный набор 22 таблиц и все турниры/сезоны. Начальный параметр
`max_partitions_per_batch=10`, `full_rebuild=false`, `mode=build`.
Пустые оба слота означают две начальные полные сборки. Время двухтурнирного
пилота не экстраполировать как доказанный срок полного объёма.

Занятость, ошибка проверки или закрытие окна приводят к ошибке задачи, а не
успешному пустому прогону. Следующая ночь продолжает сохранённые единицы сборки
того же неактивного слота. Не очищать build-state и не выставлять full_rebuild
при обычном повторе. При остановке между DELETE/INSERT и записью build-state
вся незавершённая пачка пересобирается. Общая сущность фиксируется только после
всех её частей; отдельные части не являются точками возобновления.
Частично построенный слот не переключается: downstream switch запускается
только после успешного завершения всех трёх семейств в том же DagRun.
Если отдельная партиция не помещается в 2 ГБ, остановиться, не повышать лимит.

Сохранять run_id, slot/revision, число завершённых единиц, query IDs, время,
физическое чтение, пиковую память, причиной остановки. Окно освобождается перед
обслуживанием общего Trino в 03:00 МСК. Первый полный прогон может занять
несколько ночей. Если общая таблица не успевает целиком, требуется отдельный
разбор; бесконечные повторы не означают прогресс.

## Сверка и приёмка

Сверять все 22 таблицы и все партиции с преобразованиями подтверждённого
Bronze `_current`, а не с историческими числами пилота. Сохранять входные
сигналы до и после чтения: изменившийся вход даёт неопределённый результат,
а не pass. Сигналы не доказывают отсутствие изменений содержимого при
неизменных временных метках и количестве строк. Проверить отдельно ключи,
точные сезоны и атрибуты категорий #2096: одинаковый count их не проверяет.
Каждое исключение должно иметь конкретные строки, правило и доказательство.

После обеих начальных сборок, полной сверки и отдельного подтверждения включения
расписания — три последовательные календарные даты МСК успешных обновлений.
Повторные ручные запуски за одну дату не увеличивают серию. Пропуск/сбой/неполная
сверка прерывают серию. Зелёный DAG без проверки данных недостаточен.

Сохранить материалы в `.local/tasks/2021/`, обновить единственный source-handoff,
создать отдельную приёмку #2021 и передать дежурному через monitor с readback
по установленной процедуре. Серию не начинать до первого доказанного ежедневного
обновления; назначение наблюдателя само по себе не доказывает работающий сбор.

В согласованной доставке утреннего отчёта добавить строку без тяжёлого SQL:
`FotMob Silver: <статус>; последнее обновление <МСК>; сверка <pass/fail/unknown>;
серия <N>/3; блокер <причина>`. Источник — сохранённые доказательства текущей
приёмки #2021 с датой/временем; устаревшую/отсутствующую запись показывать unknown.
Этот документ не меняет живой `/root/watchdog/morning_report.py`.

### Подготовка SQL сверки без запуска

Из отдельной проверенной рабочей копии:

```bash
python scripts/reconcile_fotmob_silver.py --slot a
python scripts/reconcile_fotmob_silver.py --slot a --scopes complete-discovery.json
```

Первая команда только печатает JSON с запросами обнаружения всех сочетаний
турнир/сезон; SQL объединяет ключи Bronze и выбранного слота, чтобы не пропустить
удалённые входные партиции. После разрешения выполнять их последовательно в
том же окне и через ограниченный курсор с 2 ГБ, сохраняя исходные результаты.
`complete-discovery.json` содержит все таблицы с областями, включая пустые:
`{table: [[competition_id, source_season_key], ...]}`; для уровня турнира сезон `''`.
Вторая команда печатает SQL сверки каждой области и частей общих таблиц.
Сам скрипт не подключается к Trino и не является работающим измерителем приёмки.

Для сравнения результатов сохранить до/после `sources`, `reader_state` и
`build_state`; отсутствие или изменение любого набора блокирует вывод о равенстве.
Обнаружение областей и сама сверка должны относиться к этим стабильным данным.
`classify` отличает `equal_counts`, `differences_require_explanation`, `incomplete`
и `inconclusive`. `equal_counts` — только равенство счётчиков, не итоговая приёмка.
Применить отдельно проверки уникальности ключей и категорий #2096. Старый
`.local/tasks/2020/reconcile.py` привязан к пилоту и не подходит для production.
