# FotMob: самостоятельный первый матчевый выпуск

Решение владельца 24.10.2026: выделить матчевые таблицы в первый выпуск, начать реализацию и проверить восемь выбранных матчей. Нематчевые семейства не блокируют эту изолированную проверку. Полная дорожная карта #1677 сохраняется для последующих выпусков.

## Что входит

25 таблиц из версионированного договора `configs/medallion/fotmob_match_silver/schema.json`: матчи, стороны, составы и прочие представления игроков, недоступные игроки, официальные лица, показатели, события, удары, координаты, динамика, погода, связанные матчи, исходные утверждения, ресурсы и покрытие.

Реализация первого прогона состоит из трёх частей:

1. `inputs.py` закрепляет сохранённые выгрузки подтверждённых Bronze payloads/manifests, проверяет точную пару турнира/сезона/матча, batch, заявленный hash, URI, parser version, success/nonstale и полноту. Вычисляет fingerprint набора. Хеш JSON-текста не выдаётся за проверку S3 blob.
2. Чистый `decoder.py` выделяет исходные записи и сохраняет их смысл, типы и происхождение. Состояние принадлежит одному вызову. Обязательная identity, ключи, связи и неизвестные формы проверяются до записи. Нечисловые необязательные значения сохраняют исходный текст и причину; ноль и прежние значения не подставляются.
3. `trino_trial.py` строит SELECT для типизации, а runner создаёт и заполняет Iceberg-таблицы. Каждый сохранённый столбец перечитывается и сравнивается с ожидаемым значением. Успешный receipt создаётся только после проверки всего комплекта. Это ограниченный первый executor, не SQL-only разворачивание всего Bronze и не промышленный batch runner.

SQL выражения отделены от DDL runner. JSON-значения логической модели физически представлены как VARCHAR с JSON-текстом, ARRAY(JSON) — как ARRAY(VARCHAR): Iceberg не получает неподдерживаемый JSON type. MAP и упорядоченные массивы остаются типизированными. Время с часовым поясом сохраняет микросекунды. Добавлены `_input_set_id` и `_silver_created_at`; source_batch_id и concrete source_pointer остаются в каждой строке. `_bronze_ingested_at` не выдумывается из timezone-less `_observed_at` выгрузки.

## Безопасная проверка

Команда запускается из корня репозитория с `PYTHONPATH=.`:

```text
python scripts/research/run_fotmob_match_silver_trial.py \
  --payloads <fixed-payload.csv> --manifests <fixed-manifest.csv> \
  --expected-payload-sha256 <verified-sha256> \
  --expected-manifest-sha256 <verified-sha256> \
  --output <new-receipt.json>
```

Без `--write` выполняется только проверка. Для реального прогона добавляются `--write --schema silver_fotmob_match_trial_<unique-run>`. Runner разрешает ровно восемь карточек и только новую схему с этим префиксом. Он не допускает `iceberg.silver`, повторное использование namespace, удаление таблиц и настройку расписания. Подключение использует уже настроенное окружение Trino, `.env` не загружается кодом.

Если прогон оборвался, частичные таблицы остаются диагностическими: у них нет успешного receipt. Повтор выполняется в новой схеме. Потребитель обязан считать доступным только комплект, имеющий проверенный receipt; пока промышленных потребителей нет. Это не подтверждение атомарного обновления рабочего Silver.

## Граница приёмки

Проверка восьми матчей и сохранённых версий одного матча подтверждает локальную реализацию договоров и реальное хранение типов. Она не закрывает все критерии #1683/#1685 и не разрешает production. Перед регулярным первым выпуском ещё нужны: чтение закреплённых Iceberg snapshots из текущего Bronze, полный источник lineage, согласованный указатель опубликованной версии, контролируемая замена всех детей, измерение нагрузки, обязательные проектные/CI проверки и отдельная приёмка выпуска. Сезоны/профили/трансферы могут выпускаться позднее.

Согласованные решения нового FotMob по точному source_season_key и контексту сохраняются. Этот эксперимент не меняет Charter других источников, старые таблицы, Gold/xref или Bronze ingest. Физические изменения общего контура оформляются отдельно.
