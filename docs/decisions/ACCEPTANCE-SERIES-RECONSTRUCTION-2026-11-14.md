# Decision: реконструкция серий приёмок по historical evidence

> Status: **active** · Created: 2026-11-14 · Owner: data-platform
> Scope: days-критерии журнала приёмок парсеров (журнал `.local/acceptance/state`, процедура
> [parser-acceptance.md](../operations/parser-acceptance.md));
> основание — решение владельца 13.11.2026 (cross-audit REPORT.md п.3: единое правило реконструкции
> серий вместо перезапуска; риск «UNKNOWN за PASS» лечится формальными критериями).
> Применение: ведущий; журнал — только через `acceptance.py`.

## 1. Область и не-цели
days-критерии приёмок парсеров (kind=days, period_seconds=86400). Одно применение = одна серия одной
записи журнала. Применяет ведущий; модели журнал не трогают. Правило НЕ изменяет критерии владельца
(не является revise), НЕ закрывает issues, НЕ переназначает/снимает monitoring, наследует все
ограничения процедуры parser-acceptance.md и движка acceptance.py.

## 2. Семантика движка (нормативная сводка, проверено по acceptance.py)
- День n = [started_at + n·86400, started_at + (n+1)·86400) UTC; интервал observe обязан совпасть с
  этой арифметикой точно; ordinal фиксирован started_at, перенумерация запрещена.
- Запись возможна только после созревания суток: end ≤ checked_at ≤ now. Дни до started_at не
  записываются — реконструкция применяется только внутри окна серии.
- Требуется series == record.series и started_at != null.
- Прогресс days-критерия = хвостовая серия подряд идущих pass от последнего ординала; unknown/fail
  обрывают видимый прогресс, но НЕ перезапускают запись. UNKNOWN не нейтрален: это не «пауза счёта».
- Переходы observe: unknown→pass/fail разрешены (восстановление по сохранённым данным); fail не
  перекрашивается; pass не стирается unknown-ом; pass→fail разрешён свежим evidence.
- change{unaffected} сохраняет серию/наблюдения/started_at (обновляет deployed_revision);
  change{affected} = новая серия — не допускается ради «прогресса».

## 3. Определение дня
Один вердикт покрывает ровно одни полные UTC-сутки. Запрещены: склейка суток (включая «агрегат за
72ч = 3 дня»), частичные сутки, вердикты по unborn-интервалам, выброс провалов/пропусков при нумерации.

## 4. Материал дня (только существующие артефакты; read-only)
a) **scheduler**: метабаза контура — dag_run/task_instance всех логических слотов суток + ранов,
   физически пересекающих интервал; для каждого ожидаемого слота — terminal-состояние или факт
   отсутствия DagRun.
b) **логи ранов**: release-scoped task-логи failed/up_for_retry инстансов.
c) **runtime-артефакты**: refresh-results/refill-отчёты слотов, violators-TSV суток, failures-журнал.
d) **поздние read-only измерения сохранённых данных** (например daily_parity.py по Bronze через
   Trino SELECT) из чистого чекаута доставленной ревизии, sha кода сверяется с релизом. Позднее
   измерение — новое свидетельство о сохранённых данных, а не исторический артефакт суток: оно
   доказывает исторический день только при доказанной применимости состояния данных к тем суткам
   (например, writers контура были остановлены с конца суток и до измерения — receipts/паузы/readback);
   иначе соответствующая нога — unknown. Запрещено изготовление артефактов, имитирующих прошлую
   работу контура.
e) **идентичность релиза**: mounts/inventory + diff-scope всех доставок внутри суток.

Каждый артефакт несёт источник, captured_at и привязку к интервалу; evidence-файлы непустые, в
каталоге задачи; журнал хранит копию и sha256. Полнота материала определяется по реестру ожидаемых
объектов (DAG, слоты, задачи, попытки), а не по наличию файлов классов. Нулевой класс (например
«0 ingest-ранов») доказан только вместе с источником, запросом/фильтрами, границами интервала и
областью объектов; оформляется файлом-отсечкой (источник/запрос, интервал, «0 строк», captured_at).
Правдоподобный, но недоказанный ноль, потерянный журнал или недоступные логи — неполнота → unknown;
пустой файл-заглушка не допускается. Для неприменимого класса фиксируется обоснование
неприменимости.

## 5. Классификация исходов ранов
Исход failed/up_for_retry классифицируется только по логу попытки: транспорт-only / writer-lock /
иной / неклассифицируемо. Отсутствие рана или лога — не классификация, а неполнота. Отрицательный
поиск (например grep без AirflowTaskTimeout) подтверждает только отсутствие строки в обследованных
логах, не выполнение контракта в целом; неизвестная причина и неполные логи оставляют проверку
unknown, кроме независимо доказанной красной ноги (→ fail).

## 6. Вердикты
- **pass** ⇔ (реестр ожидаемых слотов суток зафиксирован заранее по расписанию, действовавшему в те
  сутки, независимо от фактических запусков; каждый слот реестра имеет terminal DagRun) ∧ (все классы
  материала a–e покрыты по реестру ожидаемых объектов, включая доказанные нулевые отсечки) ∧ (все
  контрактные проверки критерия зелёные по материалу). Список ожидаемых слотов нельзя строить по
  найденным DagRun: пауза не превращает ожидаемый слот в несуществующий.
- До классификации для каждого критерия фиксируются действующие «ноги» (контрактные предикаты
  pass/fail), их сроки, scope и допустимые компенсации — по тексту критерия и прецедентам серии;
  реконструкция не добавляет и не ослабляет требования. Вердикт выводится по ногам, а не по общему
  впечатлению от материала.
- **fail** ⇔ материал подтверждает нарушение контрактной ноги критерия. Для критериев вида
  «scheduler/DQ зелёные» (пример sofascore-1370, по тексту критерия «scheduler/DQ evidence
  квалифицированы») красной ногой является провал рана собственного логического слота суток при
  доказанном отсутствии квалифицированного зелёного DQ-рана этих суток (прецедент 11.11).
  «Доказанное отсутствие» требует полного реестра ранов суток (метабаза контура, все слоты
  перечислены, включая слоты без DagRun); если реестр неполнон или компенсация неустановлена —
  unknown, а не fail. Квалифицированное scheduler/DQ evidence = ран нужной ноги/DAG, относится к
  логическому слоту этих суток, terminal success, его логи/refresh-results приложены, интервал и
  ревизия совпадают. Для критериев-контрактов (примеры sofascore-2133/2160) внешние транспортные
  провалы не fail, если соблюдён контракт повтора: обязанность повторить доказана (текст критерия/
  прецедент), наступил срок, квалифицированный повтор отсутствует в полном реестре. Неклассифицируемая
  причина провала не создаёт ни нарушения, ни подтверждения контракта. Неизмеримость паритета — не
  fail, а неполнота.
- **unknown** ⇔ любой другой случай: неполнота материала (слот без DagRun, логи недоступны, интервал
  покрыт частично), неклассифицируемая причина провала, недостаточность доказательств.
- Алгебра: подтверждённая красная нога ⇒ fail; иначе любая неполнота ⇒ unknown; иначе pass.
  UNKNOWN никогда не трактуется как pass и не устанавливает дефект парсера.

## 7. Пауза/форс-стоп владельца
Сутки целиком под задокументированной паузой (decision/receipt-файл с таймстемпом, покрывающим
сутки) без материала — unknown со ссылкой на артефакт решения; ни pass, ни fail. Пауза объясняет
неполноту, но не отменяет подтверждённую красную ногу независимо от времени её обнаружения: красный
пункт, случившийся до паузы внутри тех же суток (а также выявленный позднее по полному материалу
тех суток), остаётся красным (общая алгебра §6); исключения — только если их допускает текст
критерия. Receipt сам по себе критерий не меняет. Показатели вида overdue/missing при паузе
оцениваются по контрактному предикату критерия: без связи с предикатом они не создают ни fail,
ни pass.

## 8. Движение релиза внутри суток
Незафиксированная доставка требует change до observe этих суток. impact=unaffected не автоматичен:
он доказывается оценкой влияния на каждый критерий записи (diff-scope путей кода/DAG/конфигов/
общих библиотек, затрагивающих производителей evidence и исполнявшиеся ревизии). Если влияние не
установлено — impact=unknown и разбор по процедуре (закрытие удерживается); маскировка под
unaffected или рестарт серии «для чистоты» запрещены. started_at при unaffected не передаётся.

## 9. Запреты
- Не выдумывать материал для дней без него; день без материала = unknown; пустые сутки не успех.
- Не переносить зелёные точки между сериями; не переписывать историю дней.
- Read-only на метабазы/контейнеры/Trino; 0 запросов к сайтам источников; production не трогать.
- Журнал — только acceptance.py; чужие записи/monitoring не переназначаются.

## 10. Дисциплина readback
Snapshot до; после каждого change/observe — show/history: сверка identity (key/series/ordinal/
start/end), status, sha evidence, сохранность остальных записей. Расхождение = стоп.

## 11. Чек-лист применения (ведущий)
1. Snapshot readback записей (revision, series, started_at, deployed, текущие вердикты).
2. Для каждого дня-кандидата: созревание (end ≤ now) и точная арифметика интервала.
3. Сбор материала a–e read-only; нулевые классы — отсечки; captured_at у каждого артефакта.
4. Классификация failed/up_for_retry по логам попыток; неклассифицируемое — явно.
5. Сверка релизной идентичности суток (доставки, diff-scope, mounts).
6. Алгебра вердиктов §6; цепочка рассуждения фиксируется в evidence-манифесте дня.
7. Evidence-манифест дня: интервал, слоты, артефакты+sha256, классификация, вердикт — непустой.
8. Независимая сверка доказательств и вердиктов ДО записи (read-only модель/второй проверяющий);
   расхождение — разбор до observe: ложный pass не стирается unknown-ом, ложный fail не
   перекрашивается — цена ошибки записи необратима штатными переходами.
9. Незафиксированная доставка → change{unaffected|unknown} по §8 → readback.
10. observe с точными полями → readback записи; диапазон реконструкции: фиксируется конечный
    созревший ординал, каждый день диапазона получает вердикт (никаких выборочных зелёных участков).
11. Финальный snapshot; отчёт применения → независимое ревью (DeepSeek).

## 12. Примеры (SofaScore, ноябрь 2026)
- 11.11 (день 0, эталон): 1370=fail (паритет зелен, но 2 refresh-рана суток failed, зелёного DQ-рана
  нет); 2133=pass (writer-lock 691s без AirflowTaskTimeout; провалы транспорт-only с повторами);
  2160=pass (нарушитель 15621198 terminal-after-deadline, capture success, не транспорт).
- 12.11 (день 1): 1370=fail (слот 00:30 failed до паузы: SS-20348 scope cycle exit_code=1; слоты
  08:30/15:30 без DagRun после паузы 14:51:27Z; паритет зелен — 0 finished/0 missing/0 dupes);
  2133=unknown (1 из 3 слотов с DagRun; AirflowTaskTimeout не найден; причина SS-20348
  неклассифицируема — неполнота без подтверждённого нарушения); 2160=unknown (та же неполнота;
  SS-20348 повторён теми же сутками бэкфиллом, unretried-transport недоказуем).
- 13.11 (день 2): все три unknown — пять DAG в паузе владельца, нулевой материал, veha1 53 строки
  overdue:notstarted согласуются с паузой.

## 13. Приложение: соответствие процедуре
«Неизвестный результат можно восстановить по сохранённым данным» → §6 переходы. «Нельзя заменить
реальный провал зелёным днём… если между успешными днями пропуск, они не склеиваются» → §3, §6.
«Отсутствие доказательств не устанавливает дефект парсера» → §6 unknown, §7. «Дни без материала не
считать успехом» → §6 pass-гейт. «Для изменения версии используется change» → §8. «pass/fail требуют
непустых доказательств… журнал сохраняет копию и хеш» → §4. Ограничения владельца не изменены.
