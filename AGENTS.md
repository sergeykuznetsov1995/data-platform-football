# Data Platform Football

Airflow собирает источники в Bronze Iceberg; Trino строит Silver/Gold. Хранилище —
SeaweedFS S3, каталог — Lakekeeper. Текущий фокус — Bronze; Silver/Gold меняются
только по явной задаче.

## Вход и границы

- Начни с задания и критерия сдачи issue, затем открой [карту источников](docs/operations/README.md).
  Текущее состояние и разрешения бери из актуального handoff владельца/хоста.
  Runbook описывает процедуру, его старый snapshot не доказывает состояние production.
- На рабочем сервере прочитай host AGENTS, handoff источника и протокол общего стека
  (пути сообщает host-контекст). Если их нет в новом clone, локальная разработка
  допустима; эксплуатационные действия требуют установленных условий и разрешений.
- Для новой реализации используй отдельную ветку `codex/<задача>` от свежего
  `origin/master` и свою рабочую копию. Не переключай и не очищай чужие деревья.
- Выполняй согласованный объём. Не добавляй попутные правки Compose, Dockerfile,
  `.env`, cron или доставки. Секреты не читай без необходимости и не включай в вывод.
- Смонтированный код и runtime-скрипты — production. Перед Compose проверь реальные
  mounts, working_dir и набор конфигов по протоколу хоста. Общие `compose up`,
  `make up/up-lite/down` на общем стеке запрещены. Разрешённое обновление своего
  сервиса — с `--no-deps`; общий scheduler — согласованно из интеграционного дерева.
- Python/pytest запускай только в своей копии, не в production; его lock-файлы
  не редактируй напрямую. Не обходи пломбы, completeness, лимиты и quality gates.

## Код и архитектура

- Сбор и контракты — `scrapers/<source>/`; запуски — по карте источников;
  общие задачи — `dags/utils/`; справочники — `configs/medallion/`.
- Для transforms обязательны [Silver charter](docs/decisions/silver-charter.md),
  [SQL-памятка](dags/sql/silver/README.md), [Gold-дизайн](docs/design/gold-star-schema.md)
  и [правила имён](docs/decisions/canonical-naming.md).
- Silver сохраняет смысл и детализацию источника; агрегаты и аналитика — Gold.
  SQL transforms — SELECT без DDL/partitioning, таблицу создаёт runner.
  xref JOIN ограничивай league и season; season в Silver/Gold — varchar slug.
  Сохраняй natural-key дедупликацию и completeness guard при замене partition.
- Перед PR проверь потребителей изменённых функций, parser version, batch identity
  и runtime fingerprints: совместимость или явная миграция обязательны.

## Проверка и сдача

- Команды, Python и plugin policy — в [TESTING.md](TESTING.md). Узкий offline smoke
  проверяет запуск окружения; он не заменяет полный unit suite или обязательные CI.
- Для кода, SQL, DAG, зависимостей и конфигурации приложения: затронутые тесты между
  итерациями, полный unit suite перед PR. Для документации достаточно содержимого,
  ссылок и загрузки; изменение инструкций проверяй в новой сессии из чистой копии.
  Проверки реального Airflow и интеграций — по изменению и регламенту источника.
- Сохраняй команды/результаты, отличай новый сбой от воспроизведённого на базе.
  Выполни отдельное read-only Codex-ревью точного diff и доказательств через
  `dev-cycle`, если навык доступен; иначе используй отдельный контекст ревью.
  Один цикл на пакет, до трёх раундов; существенные замечания блокируют готовность.
- [Стадии сдачи](docs/operations/READINESS.md) различают проверенный код, merge,
  доставку и приёмку. Merge — по прямой команде или принятому процессу задачи;
  уже данное разрешение сохраняется. Доставка — автоматом по регламенту источника,
  ручная требует предусмотренного отдельного разрешения.
- Обязательные CI и защита ветки сохраняются для всех PR. Issue не закрывай по
  merge, если нужна последующая приёмка; в таком PR не используй `Closes`/`Fixes`.
  Названия и доска — в [правилах tracker](.github/PROJECT_README.md).
- Обновляй handoff и статус по доказательствам. Наблюдение продолжай в пределах
  разрешённой задачи через доступный `task-watch`; файл ожидания сам по себе
  не доказывает пробуждение. Уборка на общем хосте — штатным janitor без обходов.
