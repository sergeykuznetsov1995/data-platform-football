# FotMob Silver — схема аналитического ядра

Спецификация нового Silver FotMob (задача #2016, эпик #1677). Решения владельца — гриль
31.10.2026 (`docs/legacy-root/FOTMOB-SILVER-GRILL-2026-10-31.md`), разделы «Решения владельца
31.10», «Технические решения», «Предлагаемое ядро».

| файл | что |
|---|---|
| `core_schema.yaml` | 22 таблицы ядра: ключ, партиции, источник, колонки с типом и происхождением, колонки сырого остатка (`raw_json`) |
| `field_assignment.tsv` | все 4 929 полей реестра модели 1.1 → `column` (колонка ядра), `raw` (колонка сырого остатка) или `excluded` (с причиной) |

Кто читает: SQL `dags/sql/silver/fotmob_*.sql.j2` (#2017 матчевое семейство, #2018 сезоны/таблицы/рейтинги/плей-офф,
#2019 игроки/команды/карьера/стоимость/составы/трансферы) и аудит Charter `scripts/audit_silver_charter.py`.
Тест структуры: `tests/unit/configs/test_fotmob_silver_core_schema.py`.

## Источник и формат

- Silver читает только представления `iceberg.bronze.fotmob_*_current` (последняя подтверждённая версия
  на identity выбрана в bronze). Silver добавляет дедуп по `natural_key`
  (`ROW_NUMBER() … ORDER BY _observed_at DESC, _ingested_at DESC`).
- `from`: `<view>.<column>` | `<view>.<json_column>:<JSONPath внутри колонки>` | `derived: <правило>`.
  Для таблиц из элементов массива путь записан для представителя (`homeTeam`, `starters`, `Periods.All`,
  `[0]`), полный набор массивов — в `row_source`/`notes` таблицы.
- Все JSON-пути колонок проверены на сохранённых карточках (23 матча из
  `.local/tasks/1685-first-match-release/verify23-20261024/records.json`, игрок 789068, команда 8643,
  турнир 335 из `.local/tasks/fotmob-silver-grill-20261009/`) или запросом к bronze; непроверенные поля
  в колонки не выносились — они в сыром остатке.
- Дополнительные ключи: `rule` (правило значения колонки), `row_source`, `notes`, `context_as_key`
  (см. ниже).

## Контекст и партиции

- `scope: context` — таблица партиционирована ровно по `(competition_id, source_season_key)`, оба в ключе.
- `scope: global` — без партиций. Профили игроков/команд, составы, карьера, стоимость, трансферы — без
  турнира и сезона. Справочники `fotmob_competitions`, `fotmob_competition_seasons`,
  `fotmob_competition_season_history` помечены `context_as_key: true`: они глобальные (малы, без партиций),
  но `competition_id`/`source_season_key` — их собственный ключ, а не контекст.
- Типы: id — `BIGINT` (`competition_id` в части bronze — varchar, приводится один раз),
  `source_season_key` — `VARCHAR`, точная строка FotMob (`2026 - Apertura`), деньги `DECIMAL(38,8)` + колонка
  валюты, время с известной зоной — `TIMESTAMP(6) WITH TIME ZONE` (UTC), даты — `DATE`, JSON — `VARCHAR`.
  `transfer_event_id` — `VARCHAR` (sha256 в bronze, не число).
- Валюта: только `market_values_json` отдаёт её явно (`currency`). В составах матча, составах команд и
  трансферах FotMob валюту не передаёт — колонки `*_currency` там `NULL` (вероятно EUR, не подтверждено).

## Правило NULL (решение 09.10 №2)

- Ошибка **необязательного** поля (колонки с `conform: try`: строка → число/дата/время) → в колонке `NULL`,
  в `_conform_issues_json` добавляется `{"column": …, "raw": <сырое значение>, "reason": …}`.
  `_conform_issues_json` — JSON-массив или `NULL`, если проблем нет. Строка не теряется.
- Ошибка **ключа** (`natural_key` пустой или не приводится к типу) → строка в Silver не попадает. Такие
  строки не молчат: SQL каждой таблицы считает их отдельно (число отвергнутых строк по таблице и
  причине — в отчёте прогона/DQ задачи #2020) и сверка «Silver = bronze `_current`» объясняет разницу
  именно этим счётчиком.
- Колонки сырого остатка (`raw_json`, имена `*_json`, тип `VARCHAR`) хранят секцию/элемент целиком как
  JSON-текст; поле, которое ядро не раскладывает, «лежит» в сыром остатке своей таблицы.

## Правило самого точного сезона (решение 3)

FotMob отдаёт часть турниров двумя ключами сразу: родитель `2026` и дочерние `2026 - Apertura` /
`2026 - Clausura`. Дочерний ключ — `P || ' - ' || <часть>` (regexp `^(.+?) - (.+)$`, группа 1 — родитель).

- `fotmob_matches` (и все матчевые таблицы): строка `(competition_id, P, match_id)` отбрасывается, если тот
  же `match_id` есть у того же `competition_id` под дочерним ключом `P - <часть>`. Иначе ключ остаётся как
  есть (у турниров, где есть только дочерние или только родительский ключ, ничего не меняется).
- `fotmob_competition_seasons`: строки хранятся под всеми ключами; `parent_season_key` — группа 1, если такой
  ключ есть у того же турнира, иначе `NULL`; `has_child_seasons` — у ключа есть дочерние.
- Таблицы, рейтинги, плей-офф, стадии — под тем ключом, под которым их отдал FotMob (без перекладывания).

Проверено 31.10 на `bronze.*_current` (только чтение): 195 дочерних ключей в 7 турнирах (части `Apertura`,
`Clausura`, `Inicial`, `Final`); родитель существует у 61 из них — турниры 112 (13 из 13), 199 (34 из 34),
273 (14 из 14); у 230, 274, 335, 337 есть только дочерние ключи. Матчи: у 112 все 1 005 матчей дочерних
ключей лежат и под родителем (`2026` = 495 = `Apertura` 255 + `Clausura` 240), у 199 — 1 969 из 1 969
(`2026` = 264 = 132 + 132); у 273 матчи только под родителем `2026` (240) — остаются там.

## Правило id игрока

В составах (`fotmob_match_lineups`), статистике игроков матча (`fotmob_match_player_stats`), событиях и
ударах: id игрока `0` или отсутствует → `player_id = NULL`, строка сохраняется. Рядом — `opta_id` и
`local_player_key`:

- в составе — `'<side>:<role>:<index>'` (`home|away`, `starter|sub`, номер в массиве с 1);
- в статистике игроков — ключ строки состава, найденной по `id` (или по `optaId`, если id нет/0); если
  игрока нет в составе — `'stats:' || <ключ словаря playerStats>`.

## Сопоставление с моделью 1.1 (`field_assignment.tsv`)

`assignment`: `column` — поле закрыто колонкой ядра (`core_table.core_column`, тот же id перечислен в
`registry` колонки YAML); `raw` — поле лежит в колонке сырого остатка `core_table.core_column`;
`excluded` — поле не переносится, `reason` обязателен: «нет в bronze `_current`» (страница/секция не
сохраняется парсером и нет json-колонки с ней), «дубль …» (то же значение есть в другой колонке ядра),
служебное (SEO, ссылки на виджеты, цвета интерфейса, провенанс модели 1.1 — заменён lineage-колонками).
Генератор лежит вне репозитория: `.local/tasks/2016/gen.py` + `schema_def.py`.
